## ২. Windows প্রযুক্তিগত গবেষণা

### ২.১ Idle detection — কোন API?

| API | মূল্যায়ন |
|---|---|
| **`GetLastInputInfo`** ✅ | সবচেয়ে হালকা (~০.০০১ ms), সব Windows-এ আছে, কি-বোর্ড+মাউস দুটোই ধরে |
| Low-level hook (`WH_KEYBOARD_LL`) | প্রতিটি কী ধরে — **কার্যত কীলগার**, তাই বাদ |
| Raw Input API | নির্ভুল কিন্তু জটিল, এখানে অপ্রয়োজনীয় |

**⚠️ সীমাবদ্ধতা যা জানা থাকা দরকার:** `GetLastInputInfo` **সেশন-ভিত্তিক**। Session 0 (Windows Service) থেকে ডাকলে সবসময় ভুল ফল দেয় — এজন্যই এজেন্টকে ইউজার সেশনে চালাতে হবে।

### ২.১.১ পরে যা যাচাই করে জানা গেল *(কোড লেখার সময়, ২০২৬-০৮-১০)*

উপরের টেবিলটা ঠিক, কিন্তু "সবচেয়ে হালকা, সব Windows-এ আছে" বলে ছেড়ে দিলে চারটে ফাঁদ থেকে যেত।
এগুলো ডকুমেন্টেশন ঘেঁটে ও এই মেশিনে পরীক্ষা চালিয়ে বের করা:

| ফাঁদ | কী ঘটত | সমাধান |
|---|---|---|
| **`dwTime` ভবিষ্যতে থাকতে পারে** — Microsoft নিজেই বলে "not guaranteed to be incremental" | মাত্র ৫ সেকেন্ড এগিয়ে থাকলে সরল বিয়োগ **৪৯.৭ দিনের** ভুয়া নিষ্ক্রিয়তা দিত | `delta > 0x8000_0000` হলে শূন্য ([G44](08-Gap-Analysis.md)) |
| **`cbSize` সত্যিই যাচাই হয়** | ভুল মান → `false` + `dwTime = 0` → নিষ্ক্রিয়তা "PC চালু হওয়ার পর থেকে" | `cbSize = 8`, ফেরত মান দেখা, ব্যর্থ হলে নমুনা বাদ |
| **`Environment.TickCount64` ভবিষ্যতে বদলাতে পারে** | পরের .NET-এ unbiased ঘড়িতে গেলে dwTime-এর সাথে বিয়োগ নীরবে ভুল হবে — কোড না বদলেই | `GetTickCount64` সরাসরি P/Invoke |
| **`SendInput` মাউস-জিগলার** | শূন্য-দূরত্বের নড়াচড়াও পুরো টাইমার রিসেট করে, পর্দায় কিছু দেখা যায় না। (`SetCursorPos` করে না) | ⚠️ hook দিয়ে ধরা যেত কিন্তু সেটা কীলগিং — [G46](08-Gap-Analysis.md)-এ বিকল্প |

**যা এখনো অজানা:** স্ক্রিন লক থাকা অবস্থায় বা UAC পর্দা উঠলে `dwTime` কী করে —
Microsoft কোথাও লেখেনি। ডিজাইন ইচ্ছাকৃতভাবে এর উপর নির্ভর করে না (`locked` আসে
WTS ইভেন্ট থেকে), তবু আসল PC-তে একবার দেখে নেওয়া দরকার।

### ২.২ Session 0 Isolation — সবচেয়ে বড় টেকনিক্যাল বাধা

Windows Vista থেকে সার্ভিসগুলো Session 0-তে চলে, যেখানে কোনো দৃশ্যমান ডেস্কটপ নেই।
**পরিণতি:** সার্ভিস থেকে `BitBlt`/DXGI চালালে **কালো ছবি** আসে, `GetLastInputInfo` **ভুল** দেয়।
**সমাধান:** ট্র্যাকিং ও ক্যাপচার → ইউজার সেশনের tray app। সার্ভিস শুধু watchdog।

### ২.৩ স্ক্রিন ক্যাপচার — মাপা পারফরম্যান্স

| পদ্ধতি | ১৯২০×১০৮০-তে সময় | ঝুঁকি |
|---|---|---|
| GDI `BitBlt` | ~৪০–৬০ ms | হার্ডওয়্যার-ত্বরিত ভিডিও/গেম উইন্ডো কালো আসতে পারে |
| DXGI Desktop Duplication | ~৫–১০ ms | RDP সেশনে অকার্যকর; GPU লাগে |
| ~~Windows.Graphics.Capture~~ | ~৮–১৫ ms | ❌ বাদ — unpackaged অ্যাপে ক্যাপচার বর্ডার বন্ধ করা যায় না ([ADR-012c](05-Options-Decisions.md)) |

**নির্বাচন:** **DXGI → GDI** ([ADR-012c](05-Options-Decisions.md)) — কোড লিখে,
আসল মেশিনে চালিয়ে যাচাই করা।

মাঝখানে কিছুদিন WGC বেছে নেওয়া হয়েছিল, কারণ DXGI-র বিরুদ্ধে পাঁচটা আপত্তি ছিল:
hybrid GPU, RDP, সেশনপ্রতি ৪ প্রসেসের সীমা, portrait মনিটর কাত হয়ে আসা, আর
UAC/লক/রেজোলিউশন বদলে `ACCESS_LOST`। **আপত্তিগুলো সত্যি, কিন্তু চারটার জবাব
একটাই** — duplication ধরে না রেখে প্রতিবার নতুন করে বানানো। আর WGC-র নিজের
সমস্যাটা এড়ানোর কোনো উপায়ই ছিল না: unpackaged অ্যাপে ক্যাপচার বর্ডার বন্ধ করা যায় না।

গতির পার্থক্য এখানে অর্থহীন — ৫ মিনিটে একটা ছবি। ⚠️ তবে G46-এর **পর্দার ছাপ** আলাদা ছন্দে: ৬০ সে. পরপর, আর পর্দা জমে থাকলে ৫ সে. — শুধু প্রথম মনিটর, WebP এনকোডিং ছাড়া। নির্ভরযোগ্যতাই একমাত্র মাপকাঠি।
**DPI সতর্কতা:** এজেন্টকে `PerMonitorV2` DPI-aware করতে হবে, নাহলে 4K/স্কেল করা মনিটরে ছবি কাটা পড়ে।

### ২.৪ Session ইভেন্ট
`WTSRegisterSessionNotification` দিয়ে পাওয়া যায় — `WTS_SESSION_LOCK`, `WTS_SESSION_UNLOCK`, `WTS_SESSION_LOGON/LOGOFF`, `WTS_REMOTE_CONNECT`।
পাওয়ার ইভেন্টের জন্য `SystemEvents.PowerModeChanged` (Suspend/Resume) — ল্যাপটপ ঘুমালে ভুতুড়ে সময় যোগ হওয়া ঠেকাতে **অপরিহার্য**।

### ২.৫ স্টার্টআপ — Task Scheduler vs Run key

| পদ্ধতি | মূল্যায়ন |
|---|---|
| **Task Scheduler (At log on)** ✅ | ইউজার সহজে বন্ধ করতে পারে না, দেরিতে শুরু করা যায়, ব্যর্থ হলে রিস্টার্ট |
| Registry `Run` key | ইউজার regedit দিয়ে মুছে দিতে পারে; Task Manager → Startup থেকে ডিজেবল করা যায় |
| Startup ফোল্ডার | সবচেয়ে দুর্বল |

### ২.৬ ব্রাউজার URL — বাস্তব অভিজ্ঞতা

- Incognito/Private উইন্ডো — সম্পূর্ণ বাদ দেওয়া হবে

## ৩. আইনি ও নৈতিক গবেষণা

> ⚠️ এটি সাধারণ তথ্য, আইনি পরামর্শ নয়। চূড়ান্ত পলিসি একজন আইনজীবী দিয়ে দেখিয়ে নেবেন।

### ৩.১ বাংলাদেশের প্রেক্ষাপট
- **শ্রম আইন ২০০৬**-এ কর্মক্ষেত্রে ইলেকট্রনিক মনিটরিং নিয়ে সুনির্দিষ্ট ধারা নেই — অর্থাৎ স্পষ্ট নিষেধও নেই, স্পষ্ট অনুমোদনও নেই
- অফিসের মালিকানাধীন কম্পিউটারে, অফিসের কাজের সময়, কর্মীকে **জানিয়ে** মনিটরিং করা সাধারণভাবে গ্রহণযোগ্য চর্চা
- **ঝুঁকি তৈরি হয়** যখন: গোপনে করা হয়, ব্যক্তিগত ডিভাইসে করা হয়, অফিস সময়ের বাইরে করা হয়, বা ব্যক্তিগত যোগাযোগ (পাসওয়ার্ড, বার্তা) সংগ্রহ করা হয়
- ২০২৩-এর ডেটা সুরক্ষা সংক্রান্ত খসড়া নীতিমালা ভবিষ্যতে ব্যক্তিগত ডেটা প্রক্রিয়াকরণে সম্মতি ও উদ্দেশ্য-সীমাবদ্ধতা বাধ্যতামূলক করতে পারে — এখন থেকেই সেই মান মেনে চললে পরে বদলাতে হবে না

## ৫. স্টোরেজ ও পারফরম্যান্স গণনা

### ৫.১ স্ক্রিনশট
```
সাধারণ — দিনে ৮ ঘণ্টা active:
  ১ জন × ৮ ঘণ্টা × ১২/ঘণ্টা                =    ৯৬ ছবি/দিন
  ১৫ জন                                    = ১,৪৪০ ছবি/দিন
  × ১৫০ KB                                 =   ২১৫ MB/দিন
  × ২৬ দিন                                 =   ৫.৬ GB/মাস
  × ৩ মাস (৯০ দিন retention)               =    ১৭ GB  ✅

ভারী — দিনে ১২ ঘণ্টা active (ক্যাপচার উইন্ডো ১৬ ঘণ্টা, তাই সম্ভব):
  ১৫ জন × ১৪৪ ছবি                          = ২,১৬০ ছবি/দিন
  × ১৫০ KB × ২৬ দিন × ৩ মাস                =    ২৫ GB  ✅
```
**1 TB NVMe-র ~২.৫% (সবচেয়ে খারাপ ক্ষেত্রে)।** থাম্বনেইল ধরে ~২৭ GB।

### ৫.২ ডাটাবেস রো
```
activity_segments : ~৮০–১৫০ রো/জন/দিন   → ~১,৮০০/দিন → ~৫.৫ লাখ/বছর
app_usage         : ~২০০–৪০০ রো/জন/দিন  → ~৪,৫০০/দিন → ~১৪ লাখ/বছর
screenshots       : ১,৪৪০/দিন            → ~৪.৫ লাখ/বছর
events            : ~২০/জন/দিন           → ~৯০,০০০/বছর
─────────────────────────────────────────────────────
বছরে মোট ~২৫ লাখ রো → PostgreSQL-এর জন্য নগণ্য (~২০০ MB)
```
সঠিক ইনডেক্স থাকলে যেকোনো রিপোর্ট কুয়েরি **< ১০০ ms**।

প্রতি এজেন্ট: ~৩০০ KB/৫ মিনিট  ≈  ৩.৬ MB/ঘণ্টা  ≈  ২৯ MB/দিন
