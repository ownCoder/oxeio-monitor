# Telegram AI reply speed — 10 October 2026

User reported that the linked Telegram bot felt slow. Read-only inspection found the worker checking `getUpdates` with zero wait only every 10 seconds, so a new message could wait almost 10 seconds before processing. Warm local Qwen 1.7B inference on the VPS's 2-CPU limit took about 17–36 seconds in synthetic runs; model-dependent replies therefore felt especially slow.

Release 487 (`ed09532617ac23eb6db362268479fb62c501ae81`) changed the worker to Telegram 20-second long polling, immediate poll on startup, and a 2-second retry interval guarded against overlapping polls. The bot now shows and refreshes Telegram's typing action while preparing a reply. Ollama receives 3 CPU and a 24-hour keep-alive. Common report, ranking, explanation, planning and greeting prompts are answered from verified server facts where applicable. The first model candidate, `qwen2.5:1.5b-instruct`, answered in around 11 seconds on the VPS but produced poor Bengali in a synthetic post-deploy check. Release 488 restores `qwen3:1.7b` with `think:false`, keeping the polling and resource improvements. A synthetic comparison at 3 CPU answered a ranking correctly in 18 seconds cold after switching models and a planning prompt in 11.6 seconds, although open-ended planning wording remained generic; the application now handles that common planning intent directly.

Focused Telegram tests: 8/8 passed. API TypeScript check and lint passed before release 487; focused tests passed again after the model correction. No Telegram message was sent to a user for testing, so actual chat-to-reply time remains to be measured with a user message. No database migration, seed, OpenAI key or external AI provider was introduced. The database container and existing Telegram account link remain in place.

The owner explicitly requested a self-check. In the existing linked Telegram Web chat, `hello` and `/report` both returned in a few seconds. An open-ended capability question sent at 18:54:25 Dhaka was observed answered by 18:54:42, with an incorrect claim about academic records. The exact arrival time was between observations, so 16 seconds is an observation bound, not a precise backend latency. Release 489 (`9647ddb36ccf7f89c852bb805906c1fdffebc585`) added verified direct replies for capability and identity questions. Repeating the same question at 18:59:52 showed the accurate command list by 18:59:56, about four seconds by browser observation. Focused tests 9/9, typecheck and lint passed. Public health and release marker showed build 489. No staff member was messaged and no account link or database record was changed by the release.
