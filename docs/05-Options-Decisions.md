# 05 · Options & Decisions (ADR)

প্রতিটা গুরুত্বপূর্ণ সিদ্ধান্ত — কী কী বিকল্প ছিল, কেন এটা বেছে নেওয়া হলো, এবং এর দাম কী।

## ADR-001 · নিজে বানানো vs কেনা ✅ **নিজে বানানো**

| বিকল্প | খরচ (৩ বছর) | সময় | ডেটা কোথায় | কাস্টমাইজ |
|---|---|---|---|---|
| Hubstaff | ~৳৫.৪ লাখ | ১ দিন | USA | সীমিত |
| Time Doctor | ~৳৪.৮ লাখ | ১ দিন | USA | সীমিত |
| ActivTrak | ~৳৬.৫ লাখ | ২ দিন | USA | মাঝারি |
| **নিজস্ব** ✅ | **~৳৩৫,০০০ + শ্রম** | ৭ সপ্তাহ | **অফিসে** | **সম্পূর্ণ** |

**কারণ:** ৩ বছরে ৫ লাখ+ সাশ্রয়; ডেটা দেশের বাইরে যায় না; "শিফট ধরব না, লাঞ্চ ট্র্যাক করব না, শুধু মাসে ২০৮ ঘণ্টা" — এমন নিজস্ব নিয়ম কোনো SaaS-এ সেট করা যায় না; স্টাফ বাড়লেও খরচ বাড়ে না।
**দাম:** ৭ সপ্তাহ সময়, নিজেদের মেইনটেইন করতে হবে, বাগ নিজেদেরই ঠিক করতে হবে।

## ADR-002 · এজেন্টের ভাষা ✅ **C# / .NET 8**

| বিকল্প | সুবিধা | অসুবিধা |
|---|---|---|
| **C# .NET 8** ✅ | নেটিভ Win32 API, self-contained exe, WiX MSI, চমৎকার tray সাপোর্ট | Windows-কেন্দ্রিক |
| Python + PyInstaller | দ্রুত লেখা যায় | ৪০+ MB exe, ধীর স্টার্ট, AV প্রায় নিশ্চিতভাবে ব্লক করে |
| Rust | সবচেয়ে হালকা ও দ্রুত | Win32 binding-এ অনেক বেশি সময়, টিমের দক্ষতা কম |
| Electron | ওয়েব প্রযুক্তি | ১৫০ MB+ RAM — ১৫টা PC-তে অগ্রহণযোগ্য |
| C++ | সর্বোচ্চ নিয়ন্ত্রণ | ডেভেলপমেন্ট অনেক ধীর |

**কারণ:** ব্যাকগ্রাউন্ড এজেন্টের জন্য সবচেয়ে গুরুত্বপূর্ণ তিনটি জিনিস — কম RAM, নেটিভ API অ্যাক্সেস, আর AV-friendly হওয়া। C# তিনটিতেই ভালো, আর PyInstaller-এর AV সমস্যা এড়ায়।

## ADR-003 · Windows Service নাকি Tray App? ✅ **দুটোই**

**সমস্যা:** Windows Service চলে Session 0-তে, যেখানে ডেস্কটপই নেই — তাই সার্ভিস থেকে স্ক্রিনশট নেওয়া **অসম্ভব**।

| বিকল্প | সমস্যা |
|---|---|
| শুধু Service | স্ক্রিনশট নেওয়া যাবে না ❌ |
| শুধু Tray app | ইউজার Task Manager থেকে kill করে দিতে পারে ❌ |
| **Tray app + Watchdog Service** ✅ | ছবিও ওঠে, বন্ধ করলেও ফিরে আসে |

**গঠন:** `oXeioAgent.exe` ইউজার সেশনে (Task Scheduler → At log on) + `oXeioWatchdog.exe` সার্ভিস হিসেবে SYSTEM-এ, ৩০ সেকেন্ড অন্তর পাহারা।

| বিকল্প | মূল্যায়ন |
|---|---|

| নেটিভ Windows সার্ভিস (NSSM) | Docker লাগে না, কিন্তু আপডেট ও রিস্টোর হাতে করতে হয় |

**ফলব্যাক:** Docker সমস্যা করলে NSSM দিয়ে নেটিভে যাওয়ার পথ খোলা রাখা হবে।

## ADR-010 · Idle threshold ✅ **৬০ সেকেন্ড (কনফিগারেবল)**

| থ্রেশহোল্ড | ফল |
|---|---|
| ৩০ সে. | অতিরিক্ত সংবেদনশীল — ভাবতে গেলেই idle |
| **৬০ সে.** ✅ | আপনার নির্দেশনা — সবচেয়ে কড়া হিসাব |
| ৩ মি. (ইন্ডাস্ট্রি স্ট্যান্ডার্ড) | পড়া/ভাবা ধরা পড়ে, কিন্তু ফাঁকিও কিছুটা যায় |
| ৫ মি. | অনেক শিথিল |

**সিদ্ধান্ত:** ৬০ সে. রাখা হলো, তবে:
- ড্যাশবোর্ড থেকে বদলানো যাবে (কোড বদলাতে হবে না)
- ভুল idle সংশোধনের কোনো ব্যবস্থা নেই ([ADR-011d](#adr-011d--অনুমোদন-ব্যবস্থা--কিছুই-নেই-আপনার-সিদ্ধান্ত)) — মাসিক টার্গেট মডেলে পুষিয়ে নেওয়া যায়
- **১ মাস পর ডেটা দেখে পুনর্বিবেচনা** — কতবার ভুল idle হলো, তার রিপোর্ট থাকবে

**যা মেনে নিচ্ছি:** ডকুমেন্ট পড়া, ভিডিও দেখা, ফোনে কথা বলা — এগুলো idle দেখাবে।

## ADR-011 · লাঞ্চ ট্র্যাকিং ✅ **করা হবে না** *(আপনার সিদ্ধান্ত)*

| বিকল্প | মূল্যায়ন |
|---|---|
| নির্দিষ্ট লাঞ্চ উইন্ডো (১–২টা) | কেউ ১২:৩০-এ খেলে হিসাব গোলমাল |
| ম্যানুয়াল লাঞ্চ বাটন | স্টাফকে মনে রাখতে হয়, ভুলে গেলেই ঝামেলা |
| **কোনো লাঞ্চ ট্র্যাকিং নেই** ✅ | শুধু active সময় গোনা হয়। কে কখন খেল — সিস্টেম জানেই না |

**কারণ:** আপনার সরাসরি নির্দেশনা। পাশাপাশি এটা সবচেয়ে সরল ও ন্যায্য মডেল — একটাই প্রশ্ন থাকে, স্টাফের উপর অকারণ নজরদারিও কমে।

> ℹ️ এই ADR যখন লেখা হয়েছিল তখন টার্গেট ছিল **দৈনিক ৮ ঘণ্টা**। পরে [ADR-011b](#adr-011b--শিফট--কোনো-শিফট-নেই--মাসিক-২০৮-ঘণ্টা-আপনার-সিদ্ধান্ত)-তে সেটা **মাসিক ২০৮ ঘণ্টা** হয়েছে। লাঞ্চ ট্র্যাক না করার সিদ্ধান্তটা অপরিবর্তিত।
**প্রভাব:** DB থেকে `lunch_start/lunch_end` ও `break_sec` বাদ; state machine-এ BREAK স্টেট নেই।

| নির্দিষ্ট শিফট ৯–৬ + দৈনিক ৮ঘ | দেরি/আগে যাওয়ার ফ্ল্যাগ লাগে; রাতে কাজ করলে গোনা হয় না |
| দৈনিক ৮ঘ, সময়ের বাঁধন ছাড়া | ভালো, কিন্তু একদিন ৬ঘ পরদিন ১০ঘ করলে "ব্যর্থ" দেখায় |
| **মাসিক ২০৮ ঘণ্টা, সময়ের বাঁধন নেই** ✅ | সবচেয়ে নমনীয় ও ন্যায্য — মাস শেষে মোট ঘণ্টাই আসল |

**যা বাদ গেল:** `shifts` টেবিল, OFF_SHIFT স্টেট, late/early-leave ফ্ল্যাগ, দৈনিক টার্গেট, workdays অ্যারে।
**যা যোগ হলো:** `work_policies` ও `monthly_summary` টেবিল, pace (এগিয়ে/পিছিয়ে) হিসাব।
**দাম:** কে কখন অফিসে ছিল তা আর বোঝা যাবে না — কিন্তু আপনি সেটা চানও না।

## ADR-011c · স্ক্রিনশটের সময়সীমা ✅ **০৭:০০–২৩:০০** *(অনুমোদিত)*

সময় **গণনা** ২৪ ঘণ্টা রাখা যুক্তিসঙ্গত। কিন্তু **স্ক্রিনশট**ও ২৪ ঘণ্টা তুললে:

| ঝুঁকি | ব্যাখ্যা |
|---|---|
| ব্যক্তিগত জীবন ধরা পড়া | রাত ২টায় ল্যাপটপে ব্যক্তিগত কাজ করলে তার ছবিও উঠবে |
| আইনি দুর্বলতা | "আনুপাতিকতা" নীতির বিরুদ্ধে যায় |
| আস্থাহানি | স্টাফের কাছে "সারাক্ষণ নজরদারি" মনে হবে |
| স্টোরেজ | সামান্য বাড়বে (বড় সমস্যা নয়) |

| বিকল্প | মূল্যায়ন |
|---|---|
| **সময় ২৪ঘ · ছবি ০৭:০০–২৩:০০** ✅ **নির্বাচিত** | রাতে কাজ করলেও ঘণ্টা পুরোপুরি গোনা হয়, শুধু ছবি ওঠে না |
| ছবিও ২৪ ঘণ্টা | সম্পূর্ণ কভারেজ, কিন্তু উপরের ঝুঁকিগুলো নেয় |
| ছবি সম্পূর্ণ বন্ধ | সবচেয়ে নিরাপদ, কিন্তু আপনার মূল চাহিদাই বাদ |

**সিদ্ধান্ত:** অনুমোদিত। `work_policies.screenshot_from = '07:00'`, `screenshot_to = '23:00'` — সেটিংস থেকে বদলানো যাবে।

## ADR-011d · অনুমোদন ব্যবস্থা ✅ **কিছুই নেই** *(আপনার সিদ্ধান্ত)*

| বিকল্প | মূল্যায়ন |
|---|---|
| পূর্ণ approval ফ্লো (মিটিং claim + ছুটি + ম্যানুয়াল টাইম) | ভুল idle সংশোধন করা যেত, কিন্তু প্রতিদিন approve/reject করতে হতো |
| শুধু মিটিং claim | কম ঝামেলা, তবু স্টাফকে বাটন চাপতে হয়, আপনাকে দেখতে হয় |
| **কোনো অনুমোদন নেই** ✅ | active = গোনা হয়, ব্যস। শূন্য রক্ষণাবেক্ষণ |

**কারণ:** আপনার সরাসরি নির্দেশনা — *"only time tracker enough"*। মাসিক ২০৮ ঘণ্টার মডেলে এটা যুক্তিসঙ্গতও: একদিন মিটিংয়ে ২ ঘণ্টা গেলে সেদিন কম হবে, কিন্তু মাসজুড়ে পুষিয়ে নেওয়া যায়। দৈনিক টার্গেট থাকলে অনুমোদন লাগত, মাসিক টার্গেটে লাগে না।

**যা বাদ গেল:** `time_claims` · `leave_types` · `leave_requests` · `leave_balances` টেবিল · MEETING স্টেট · Meeting/Break বাটন · Approvals পেজ · ৪৮ ঘণ্টার auto-approve নিয়ম · ২টি API endpoint।

**দাম:** ভুল idle (যেমন দীর্ঘ মিটিং বা ডকুমেন্ট পড়া) সংশোধনের কোনো উপায় নেই — ওই সময়টা শুধুই গোনা হবে না। মাসিক মডেলে এটা সহনীয়।

**পরে দরকার হলে:** ছুটির মডিউল আলাদাভাবে যোগ করা যাবে; মূল ট্র্যাকারে হাত দিতে হবে না।

## ADR-011e · সিস্টেমের দোষে হারানো ঘণ্টা ✅ **owner-এর audited সংশোধন**

ADR-011d স্টাফের claim ব্যবস্থা বাদ দিয়েছিল — সেটা বহাল আছে। কিন্তু ওই সিদ্ধান্তে একটা ক্ষেত্র ভাবা হয়নি: **স্টাফের কোনো দোষ ছাড়াই ঘণ্টা হারানো।** এজেন্ট ক্র্যাশ করল, সার্ভার ৩ দিন ডাউন ছিল, PC বদলাতে হলো — কাজ হয়েছে, কিন্তু রেকর্ড নেই। ঠিক করার কোনো পথও নেই।

| বিকল্প | মূল্যায়ন |
|---|---|
| কিছুই না করা | ঘণ্টা চিরতরে হারায়। স্টাফ ঠিকই টের পাবে, আর পে-রোলের দিন এটা নিয়েই ঝামেলা হবে। সিস্টেমের প্রতি আস্থাও যাবে |
| স্টাফের claim ফিরিয়ে আনা | ADR-011d-র সিদ্ধান্ত উল্টে যায়; প্রতিদিন approve/reject করতে হয় |
| **owner-এর audited সংশোধন** ✅ | স্টাফের কিছু করার নেই। downtime-এর প্রমাণ সিস্টেম নিজেই দেখায়, owner এক ক্লিকে ঠিক করে দেয় |

**কেন এটা approval workflow নয়:** approval-এ স্টাফ *চায়*, owner *অনুমোদন করে* — প্রতিদিনের কাজ। এখানে স্টাফ কিছুই চায় না; শুধু সিস্টেম ব্যর্থ হলে owner মেরামত করে। বছরে হয়তো ৩–৪ বার লাগবে।

**যে ছয়টা নিয়ম এটাকে ছোট ও নিরাপদ রাখে:** শুধু owner · `reason` বাধ্যতামূলক · কাঁচা `activity_segments` কখনো এডিট হয় না · heartbeat-গ্যাপ থেকে প্রস্তাবিত পরিমাণ · তার বেশি দিলে `beyond_evidence` ফ্ল্যাগ · **স্টাফ নিজেও কারণসহ দেখতে পায়**। ডিলিট নেই, শুধু revoke।

**দাম:** একটা টেবিল (`time_adjustments`), তিনটে endpoint, আর `worked_sec` / `credited_sec` — দুটো আলাদা সংখ্যা রাখতে হবে। বিস্তারিত: [07 §2.1-ঙ](07-Technical-Spec.md)।

## ~~ADR-012~~ · স্ক্রিন ক্যাপচার API ⚠️ **বাতিল — [ADR-012b](#adr-012b-dxgi-কে-যে-পাঁচটা-কারণে-বাদ-দিয়েছিল--প্রতিটার-জবাব) দেখুন**

মূল সিদ্ধান্ত ছিল **DXGI Desktop Duplication, GDI ফলব্যাক সহ** — গতির (~৮ ms) ভিত্তিতে।
পরে API-গুলো যাচাই করে দেখা গেল গতি এখানে অপ্রাসঙ্গিক ছিল, আর DXGI-র সমস্যাগুলো
"RDP-তে কাজ করে না" বলে যতটা ভাবা হয়েছিল তার চেয়ে অনেক গভীর।

## ~~ADR-012b~~ · স্ক্রিন ক্যাপচার API ⚠️ **বাতিল — [ADR-012c](#adr-012c--স্ক্রিন-ক্যাপচার-api-চূড়ান্ত--dxgi-প্রধান-gdi-ফলব্যাক) দেখুন**

> নিচের বিশ্লেষণটা রেখে দেওয়া হলো, কারণ ADR-012c ঠিক এটার প্রতিটা আপত্তির
> জবাব দিয়েই দাঁড়িয়ে আছে। এখানকার হলুদ বর্ডারের অংশটা ভুল প্রমাণিত —
> **বর্ডার Windows 10-এ সীমাবদ্ধ নয়, আর আমাদের ক্ষেত্রে সেটা বন্ধ করাও যায় না।**

| API | মূল্যায়ন |
|---|---|
| ~~DXGI Desktop Duplication~~ | ❌ Microsoft Hybrid ল্যাপটপে discrete GPU-র বিপরীতে **ডিজাইনেই** `DXGI_ERROR_UNSUPPORTED` · RDP-তে কালো বা ব্যর্থ (ড্রাইভারভেদে) · সেশনপ্রতি **৪ প্রসেসের সীমা**, যা Zoom/Teams/OBS খেয়ে ফেলে · portrait মনিটরের ছবি কাত হয়ে আসে · UAC প্রম্পট, লক, রেজোলিউশন বদল — প্রতিটিতে `DXGI_ERROR_ACCESS_LOST` |
| **Windows.Graphics.Capture** ✅ | কম্পোজিটর-ভিত্তিক, উপরের একটাও সমস্যা নেই। `IGraphicsCaptureItemInterop.CreateForMonitor` দিয়ে প্রতি মনিটরে একটা করে |
| **GDI `BitBlt`** ✅ *(ফলব্যাক)* | সব জায়গায় চলে। হার্ডওয়্যার-ত্বরিত ভিডিও কালো আসতে পারে — সেটা মেনে নিয়ে `capture_degraded` ট্যাগ করা হবে |

**কৌশল:** চালু হওয়ার সময় একবার `GraphicsCaptureSession.IsSupported()` **এবং** একটা
পরীক্ষামূলক ক্যাপচার — দুটোই সফল হলে WGC, নইলে GDI। পছন্দটা heartbeat-এ পাঠানো হয়,
যাতে ড্যাশবোর্ডে দেখা যায় ফ্লিটের কোন মেশিন কোন ইঞ্জিনে চলছে।

`IsSupported()` কেবল `bool` ফেরত দেয়, ব্যতিক্রম ছোড়ে না — তাই শুধু ওটা দেখে ছেড়ে দিলে
ব্যর্থতা নীরব হতো। সেজন্যই পরীক্ষামূলক ক্যাপচারটা প্রোবের অংশ।

**দাম:** WinRT interop একটু জটিল (`CsWinRT`, COM interface), আর দুটো ইঞ্জিন মেইনটেইন করতে হবে।
প্রতি ৫ মিনিটে একটা ছবির জন্য গতির পার্থক্য অর্থহীন — **নির্ভরযোগ্যতাই একমাত্র মাপকাঠি**।

### ⚠️ হলুদ বর্ডার — স্টাফ যেটা চোখে দেখবে

WGC ব্যবহার করলে **Windows 10-এ প্রতিটি ছবি তোলার সময় মনিটরের চারপাশে হলুদ বর্ডার
ঝিলিক দেয়** — প্রায় ১০০–৩০০ মিলিসেকেন্ড, প্রতি ৫ মিনিটে একবার।
`IsBorderRequired = false` দিয়ে এটা বন্ধ করা যায়, কিন্তু সেটা **শুধু Windows 11-এ কাজ করে**;
Windows 10-এ ওই সেটিং নিষ্ক্রিয়। GDI ফলব্যাকে কোনো বর্ডার নেই।

| বিকল্প | মূল্যায়ন |
|---|---|
| **বর্ডার মেনে নেওয়া** ✅ | স্টাফ-মনিটরিং টুলে এটা আসলে **সম্মতির সংকেত** — লুকানোর কিছু নেই বলেই আমরা tray আইকনও দৃশ্যমান রাখছি |
| বর্ডার এড়াতে সব মেশিনে GDI | নির্ভরযোগ্যতা কমে (ভিডিও/DRM উইন্ডো কালো আসে) — উল্টো ক্ষতি |
| বর্ডার লুকানোর কৌশল খোঁজা | ❌ OS ইচ্ছাকৃতভাবে এটা দেখায়। ফাঁকি দেওয়ার চেষ্টা মানে গোপন নজরদারি — [04-Features § L](04-Features.md)-এর সরাসরি বিরুদ্ধে |

**যে অসমতাটা মনে রাখতে হবে:** Windows 11-এর স্টাফ কিছুই দেখবে না, Windows 10-এর স্টাফ
ঝিলিক দেখবে। কেউ জিজ্ঞেস করলে "তোমার PC-তে হয় কেন, ওরটায় হয় না?" — উত্তরটা যেন
আগে থেকেই তৈরি থাকে। **তাই এটা মনিটরিং পলিসিতে লিখে দিতে হবে**
([06-Research § ৩.৩](06-Research.md)), রোলআউটের দিন আবিষ্কার করার জিনিস নয়।

## ADR-012c · স্ক্রিন ক্যাপচার API *(চূড়ান্ত)* ✅ **DXGI প্রধান, GDI ফলব্যাক**

ADR-012b লেখার সময় ধরে নেওয়া হয়েছিল হলুদ বর্ডারটা কেবল Windows 10-এর সমস্যা,
আর Windows 11-এ `IsBorderRequired = false` দিয়ে বন্ধ করা যাবে। **দুটোই ভুল ছিল।**

`IsBorderRequired` সেট করতে হলে MSIX প্যাকেজের `graphicsCaptureWithoutBorder`
capability লাগে, তার সাথে `GraphicsCaptureAccess.RequestAccessAsync` দিয়ে
ব্যবহারকারীর সম্মতি নিতে হয়। আমাদের এজেন্ট **unpackaged** আর **unattended** —
দুটো শর্তের একটাও পূরণ হয় না। অর্থাৎ বর্ডার **সব মেশিনেই** ঝিলিক দিত,
প্রতি মনিটরে দিনে প্রায় ১৯০ বার।

সেটা মেনে নেওয়ার মতো জিনিস নয়। আর মেনে নেওয়ার যুক্তিটাও দুর্বল ছিল: স্বচ্ছতা
আসে **সবসময় দৃশ্যমান tray আইকন** আর **সই করা লিখিত পলিসি** থেকে
([04-Features § J](04-Features.md))। প্রতি ৫ মিনিটে একটা ঝিলিক ওতে নতুন কিছু
যোগ করে না, শুধু বিরক্তি বাড়ায় — আর ওই বিরক্তির স্বাভাবিক "সমাধান" হিসেবে
কেউ এজেন্ট লুকানোর কথা তুলত, যেটা আমাদের নীতির সরাসরি বিরুদ্ধে।

### ADR-012b DXGI-কে যে পাঁচটা কারণে বাদ দিয়েছিল — প্রতিটার জবাব

| ADR-012b-র আপত্তি | কেন আর প্রযোজ্য নয় |
|---|---|
| হাইব্রিড GPU-র ল্যাপটপে `DXGI_ERROR_UNSUPPORTED` | মনিটরের HMONITOR মিলিয়ে **যে অ্যাডাপ্টারে সেটা লাগানো ঠিক সেটাতেই** ডিভাইস বানানো হয় — এটাই ডকুমেন্টেড সমাধান। তাছাড়া অফিসের ১৫টাই ডেস্কটপ |
| RDP-তে কালো বা ব্যর্থ | `SESSION_DISCONNECTED` ধরা পড়ে, ওই স্লট GDI-তে ওঠে। ডেস্কটপ PC-তে RDP এমনিতেও স্বাভাবিক নয় |
| সেশনপ্রতি ৪ duplication-এর সীমা | duplication টেকে **~২৫০ মি.সে.**, তারপর ভেঙে ফেলা হয়। সীমার একটা ঘর সারাক্ষণ দখল করে রাখা হয় না। ছুঁয়ে গেলে `NOT_CURRENTLY_AVAILABLE` → GDI |
| portrait মনিটরে ছবি কাত | `DXGI_OUTDUPL_DESC.Rotation` দেখে ঘোরানো ডিসপ্লে **আগেই** শনাক্ত করে GDI-তে দেওয়া হয় — GDI composed ডেস্কটপ পড়ে, তাই ঘূর্ণন ওর কাছে এমনিতেই ঠিক |
| UAC/লক/রেজোলিউশন বদলে `ACCESS_LOST` | duplication ধরে রাখলে এটা সমস্যা। প্রতিবার নতুন করে বানানোয় `ACCESS_LOST` ঘটার সময়ই পায় না |

লক্ষণীয়: পাঁচটার মধ্যে চারটার জবাবই একই নকশা থেকে আসে — **প্রতিবার পুরো চেইন
নতুন করে বানানো ও ভাঙা।** ৫ মিনিটে একটা ছবির জন্য এর খরচ শূন্যের কাছাকাছি,
অথচ এটাই DXGI-র প্রায় সব দুর্বলতা মুছে দেয়।

### একটা ভুল ধারণা সংশোধন

ADR-012b (আর 09-Build-Log) ধরে নিয়েছিল WGC/DXGI নিলে **DRM কনটেন্টের ছবি**
পাওয়া যাবে। **যাবে না।** DRM-সুরক্ষিত উইন্ডো তিনটে ইঞ্জিনেই কালো আসে — ওটা
OS-এর কনটেন্ট সুরক্ষা, ক্যাপচার API-র সীমা নয়।

GDI-র উপর DXGI যা সত্যিই দেয়: **হার্ডওয়্যার-ত্বরিত ভিডিও** আর
**exclusive-fullscreen** — এই দুটোই GDI-তে কালো আসে। বাড়তি পাওনা
`ProtectedContentMaskedOut` — OS নিজেই বলে দেয় DRM কনটেন্ট বাদ পড়েছে,
যেটা GDI-তে আন্দাজ করা ছাড়া উপায় ছিল না।

### ⭐ দুটো ইঞ্জিন ঠিক একে অন্যের ফাঁক ভরে

DXGI ছবি দেয় **কেবল তখনই যখন পর্দায় কিছু বদলায়**। পর্দা একদম স্থির থাকলে ও
কিছুই দেয় না — কিন্তু স্থির পর্দায় GDI নিখুঁত, কারণ GDI-র কালো আসার একমাত্র
কারণই চলমান ভিডিও। অর্থাৎ যে অবস্থায় একটা অকেজো, ঠিক সেই অবস্থায় অন্যটা নিখুঁত।

তাই "কোনো পরিবর্তন নেই" **ব্যর্থতা হিসেবে গোনা হয় না** — নইলে শান্ত অফিসের PC-তে
কয়েক স্লট পরেই DXGI বিরতিতে চলে যেত, আর কেউ ভিডিও চালানো শুরু করলে ঠিক তখনই
সেটা ঘুমিয়ে থাকত।

### যা হাতে-কলমে যাচাই করা হয়েছে

দুই-মনিটরের মেশিনে চালিয়ে দেখা হয়েছে — এবং **প্রথম চেষ্টাটা এমনভাবে ভুল ছিল
যেটা শেখার মতো:** `AcquireNextFrame` সফল, HRESULT ঠিক, মাপ ঠিক (১৯২০×১০৮০,
pitch ৭৬৮০) — অথচ প্রতিটা পিক্সেল শূন্য।

`AccumulatedFrames == 0` মানে ওই ফ্রেমে ডেস্কটপের ছবিই বসানো হয়নি। **শুধু
ফেরত মান দেখে সন্তুষ্ট হলে মাসের পর মাস নিখুঁতভাবে কালো ছবি জমত** — আর
সেগুলো "স্টাফের পর্দা সত্যিই কালো ছিল"-র থেকে আলাদা করা যেত না।
খালি ফ্রেম ছেড়ে দিয়ে আসল ছবির অপেক্ষা করার পর ৬০/৯৬ KB-র পরিষ্কার ছবি এসেছে।

**দাম:** ~৪০০ লাইন হাতে-লেখা COM interop, যেখানে একটা vtable স্লট ভুল হলে
ভুলটা নীরব। তাই প্রতিটা স্লট, IID ও স্ট্রাক্ট লেআউট SDK হেডার থেকে গুনে
মেলানো, আর প্রতিটার পাশে হেডারের লাইন নম্বর লেখা। কোনো নতুন NuGet নির্ভরতা
লাগেনি, TFM বদলাতে হয়নি।

## ADR-014 · কোড সাইনিং ✅ **নিজে সই করা (self-signed), কেনা নয়** *(সংশোধিত ১২ আগস্ট)*

**সিদ্ধান্ত আপনার** *(১২ আগস্ট)* — *"নিজে সই করা (self-signed) eta korO … amar only 15 jon staff er jonno eto taka spend korte caina."*

| বিকল্প | খরচ | ফল |
|---|---|---|
| কিছুই না | ০ | ইনস্টলে "Unknown publisher" — অ্যাডমিন একবার "Run anyway" |
| **নিজে সই + Trusted Publishers** ✅ | **০** | ওই ডায়ালগটাই আর আসে না; AV-র চোখেও ভালো |
| Azure Trusted Signing | ~$১০/মাস | Microsoft-এর সেবা, পরিচয় যাচাই লাগে |
| OV কোড সাইনিং | ~$৬০–২০০/বছর | বাইরে বিলি করলে কাজে লাগে |
| EV কোড সাইনিং | ~$২৫০+/বছর | SmartScreen-এ সাথে সাথেই সবুজ, হার্ডওয়্যার টোকেন লাগে |

⚠️ **আগের সংস্করণে খরচের অঙ্কটা বেশি বলা ছিল** (এবং কথোপকথনে "~$২০০/বছর" বলা
হয়েছিল) — ওটা EV-র প্রান্ত। OV অনেক সস্তা, আর Microsoft-এর নিজের
Trusted Signing মাসে ~$১০।

### ⭐ কেন কেনার দরকার নেই — তিনটে কারণ

**১· SmartScreen এখানে জ্বলেই না।** ওই সতর্কতা আসে *Mark-of-the-Web* থেকে,
অর্থাৎ ফাইলটা ব্রাউজার দিয়ে ইন্টারনেট থেকে নামালে। MSI যাবে নেটওয়ার্ক শেয়ার
বা পেনড্রাইভে, আর চলবে `msiexec` দিয়ে — MOTW বসেই না।

**২· auto-update পথেও নয়।** এজেন্ট MSI নামায় নিজের `HttpClient` দিয়ে,
ব্রাউজার দিয়ে নয় — তাই সাইলেন্ট ইনস্টল আটকায় না।

**৩· AV-র আসল সমাধান exclusion, সই নয়।** ⚠️ স্ক্রিনশট তোলা + উইন্ডো টাইটেল
পড়া + লগঅনে চালু হওয়া — এই তিনটে একসাথে যেকোনো heuristic AV-র চোখে
spyware-ই। সই থাকলে সেটা **কমে, যায় না**; `defender-exclusions.ps1`-ই
আসল উত্তর (H09)।

### ✅ যা বানানো হয়েছে *(১২ আগস্ট)*

| | |
|---|---|
| `deploy/make-code-cert.ps1` | ৫ বছরের সার্ট · `.cer` (বিলির জন্য) · `.pfx` (⚠️ **হারালে একই পরিচয়ে আর সই করা যাবে না**) · thumbprint |
| `build.ps1 -SignWith <thumbprint>` | publish → **দুটো exe-তে সই** → wix → MSI-তে সই |
| `deploy/trust-publisher.ps1` | প্রতিটা PC-তে `.cer` → **Trusted Root ও Trusted Publishers** |

⚠️ **exe-গুলোতেও সই করতে হবে, শুধু MSI-তে নয়** — AV মোড়কের চেয়ে ভেতরের
`oXeio.Agent.exe`-কেই বেশি সন্দেহ করে। ⭐ তাই সই বসে **wix build-এর আগে**;
পরে করলে MSI-র ভেতরে সই-ছাড়া কপিটাই বসে থাকত, অথচ মোড়কে সই দেখে মনে হতো
সব ঠিক আছে। (MSI খুলে বের করে যাচাই করা হয়েছে।)

⚠️ সার্ট না দিলে `build.ps1` আগের মতোই চলবে, কোনো ভুল ছাড়া — নইলে ডেভ
মেশিনে বিল্ড করাই আটকে যেত।

### ⚠️⚠️ দুটো ফাঁদ, দুটোই মেপে ধরা পড়েছে

**১· `.cer` দুই স্টোরে বসাতে হয়, এক জায়গায় নয়।**
কেনা সার্টে শুধু Trusted Publishers-ই যথেষ্ট, কারণ তার ইস্যুকারী
(DigiCert ইত্যাদি) Windows-এ আগে থেকেই বসানো। ⚠️ কিন্তু self-signed সার্ট
**নিজেই নিজের ইস্যুকারী** — Trusted **Root**-এ না বসালে চেইন ভাঙা থাকে,
আর Publishers-এ থাকা সত্ত্বেও ডায়ালগটা আসতেই থাকে।

**২· `Set-AuthenticodeSignature`-এর `Status` মিথ্যে বলে — প্রায়।**
সার্ট বানানোর পর প্রথম বিল্ডেই সই "ব্যর্থ" হলো:

> `UnknownError — A certificate chain processed, but terminated in a root
> certificate which is not trusted by the trust provider`

⚠️ অথচ ফাইলে সই **বসে গেছে**, টাইমস্ট্যাম্পও হয়েছে। `Status` আসলে বলে
*"এই মেশিন সইটা যাচাই করতে পারল কি না"* — আর বিল্ড-মেশিন নিজের সার্টটা
Trusted Root-এ বসায়নি বলে পারেনি। ⚠️⚠️ প্রথমে `Status -ne 'Valid'` হলেই
throw করা ছিল, আর তাতে **সই করা অসম্ভব** হয়ে যেত — অথচ আসল সমস্যা কিছুই
ছিল না। এখন প্রশ্নটা করা হয় *"আমাদের সার্ট দিয়ে সই বসেছে তো?"*।

⭐ **টাইমস্ট্যাম্প বাধ্যতামূলক** (`-NoTimestamp` দিয়ে স্পষ্ট করে বাদ দেওয়া
যায়)। ছাড়া সই করলে সার্টের মেয়াদ শেষ হওয়ার দিন **আগের সব বিল্ডের সই
একসাথে অচল** হতো — অর্থাৎ ৫ বছর পর পুরোনো MSI দিয়ে কোনো মেশিন আর ঠিক
করা যেত না।

## ADR-016 · অথেনটিকেশন ✅ **httpOnly JWT cookie**

localStorage-এ টোকেন রাখলে XSS-এ চুরি হয়। httpOnly cookie + SameSite=Strict + CSRF টোকেন — ২ জন ইউজারের জন্য যথেষ্ট এবং নিরাপদ। ঐচ্ছিক TOTP 2FA যোগ হবে ফেজ ৬-এ।

## ADR-017 · এজেন্টের কোড ভাগ ✅ **নিয়ম প্ল্যাটফর্ম-মুক্ত, Win32 আলাদা**

[03-Project-Map](03-Project-Map.md)-এর পরিকল্পনায় `oXeio.Core/Native/` ছিল — অর্থাৎ
Win32 interop শেয়ার্ড লাইব্রেরির ভেতরে। বাস্তবায়নে উল্টো করা হয়েছে।

| বিকল্প | মূল্যায়ন |
|---|---|
| Core-এ Win32 (মূল পরিকল্পনা) | সব এক জায়গায়, কিন্তু ঘণ্টার হিসাব তখন **শুধু আসল ডেস্কটপে হাতে চালিয়েই** যাচাই করা যেত |
| **Core = শুধু নিয়ম (`net8.0`), Win32 = Agent (`net8.0-windows`)** ✅ | `IdleStateMachine` বাইরে থেকে মাত্র তিনটে তথ্য নেয় — সময়, শেষ ইনপুট কতক্ষণ আগে, লক কি না। ফলে পুরো নিয়ম ইউনিট টেস্টে ধরা যায় |

**কারণ:** এই প্রজেক্টে ভুল হিসাব মানে ভুল পে-রোল। নিয়মগুলো আলাদা রাখায় ৫২টি টেস্ট
প্রতি PR-এ সাধারণ Linux runner-এ চলে, আর পরে কিছু ভাঙলে **হিসাবের নিয়মে সন্দেহ করতে হয় না** —
সমস্যাটা Win32 স্তরেই খোঁজা যায়।

**দাম:** CI-তে দুটো job (Linux-এ নিয়ম, Windows-এ পুরোটা), আর কিছু জিনিস দুবার
লিখতে হয়েছে — যেমন `DhakaTime` সার্ভারের `dhaka-time.ts`-এর প্রতিরূপ। দুটোরই আলাদা টেস্ট আছে,
কারণ দুই দিকে `work_date` আলাদা হলে ঘণ্টার হিসাব নীরবে ভুল হতো।

## ADR-023 · বেতন ও ঘাটতির টাকা ✅ **রাখা হবে, শুধু owner দেখবে**

**সিদ্ধান্ত আপনার** *(১০ আগস্ট)* — অফিসের ১২ জনের বেতন দিয়ে জিজ্ঞেস করা হয়েছিল
এটা রাখা হবে কি না। উত্তর: রাখো, আর ঘাটতির হিসাব চাই।

এতে সিস্টেমের চরিত্র একটু বদলায়: এতদিন এটা শুধু **ঘণ্টা** গুনত, এখন একটা
জায়গায় **টাকার** সিদ্ধান্তও দেবে। তাই আলাদা করে লিখে রাখা।

**হিসাবটা:**
```
ঘণ্টাপ্রতি হার = মাসিক বেতন ÷ মাসিক টার্গেট ঘণ্টা   (২০৮, পলিসি থেকে — হার্ডকোড নয়)
কর্তন         = বেতন × ঘাটতি-সেকেন্ড ÷ টার্গেট-সেকেন্ড
প্রদেয়        = বেতন − কর্তন   (কখনো ঋণাত্মক নয়)
```

**তিনটে জিনিস ইচ্ছাকৃতভাবে এভাবে করা:**

| | কেন |
|---|---|
| হারটা **আলাদা করে round করা হয় না** | ১০০০০ ÷ ২০৮ = ৪৮.০৭৬৯… ভাগ যায় না। হার আগে round করে ঘণ্টা দিয়ে গুণ করলে ২০ ঘণ্টায় ৯৬১.৬০ আসত, সঠিক ৯৬১.৫৪। ভুলটা ছোট, কিন্তু **সবসময় একই দিকে ঝোঁকে — কর্মীর বিপক্ষে** |
| সব হিসাব **পয়সায় (integer)** | টাকা কখনো binary float-এ নয় |
| **OT-র টাকা হিসাব করা হয় না** | ঘণ্টাটা দেখানো হয়, টাকা নয়। হার ১× না ১.৫× সেটা ব্যবসায়িক সিদ্ধান্ত, আর সেটা কেউ নেয়নি ([O4](#-এখনো-খোলা-সিদ্ধান্ত)) |

**অ্যাক্সেস:**
`monthly_salary` কলামটা **একমাত্র** `PayrollService` পড়ে; আর কোনো endpoint ওটা
select-ই করে না। কন্ট্রোলারে `@Roles(owner)` **ক্লাস-লেভেলে** বসানো, মেথডে নয় —
যাতে পরে কেউ নতুন endpoint যোগ করলে সেটাও আপনাআপনি owner-only থাকে।
ম্যানেজার (Belal) বেতন দেখতে পাবেন না।

⚠️⚠️ **আর লেখার দিকটাও বন্ধ — সেটা আলাদা করে করতে হয়েছে** *(১৫ আগস্ট,
[ADR-027](#adr-027--ম্যানেজারের-অ্যাক্সেস--staff--holidays--categories))*। ম্যানেজার কর্মী
এডিট করতে পারার দিন থেকে `redact.ts`-এর ছাঁকনিটা আর যথেষ্ট নয়: ওটা **উত্তর**
ছাঁকে, **অনুরোধ** নয়। তাই `EmployeesService.assertMaySetSalary()` ম্যানেজারের
পাঠানো `monthlySalary` দেখলে **৪০৩** দেয়, `null` হলেও।

⭐ নীরবে ফিল্ডটা ফেলে দেওয়া হয় **না** — তাহলে ম্যানেজার ভাবতেন বেতন বসে গেছে।
আর নীরবে **নিলে** অবস্থাটা দুটোর চেয়েও খারাপ হতো: তিনি এমন একটা ঘরে লিখতেন
যেটা তিনি **পড়তেও** পারেন না, অর্থাৎ নিজের ভুল নিজে দেখেও ধরতে পারতেন না —
আর সেটা ধরা পড়ত মাসের শেষে পে-রোলে।

বেতন দেখা `audit_log`-এ `payroll_view` হিসেবে লেখা হয় — স্ক্রিনশট দেখার মতোই,
কারণ সংবেদনশীলতায় এটা তার চেয়ে কম নয়।

**যেটা বসানো নেই সেটা শূন্য ধরা হয় না।** কারো বেতন না থাকলে শিটে তার সারি
আসে ফাঁকা ঘর নিয়ে, আর নামটা `missingSalary`-তে আলাদা করে বলা হয় — নইলে
"বেতন বসানো হয়নি" নীরবে "বেতন শূন্য" হয়ে যেত।

## ADR-024 · এজেন্ট কীভাবে ডিভাইস চেনে ✅ **স্টাফের নিজের লগইন, কোড ফলব্যাক**

**সিদ্ধান্ত আপনার** *(১২ আগস্ট)* — MSI-তে ডাবল-ক্লিক করে *"SERVERURL দিতে
হবে"* দেখে বলা হলো: *"install process ta simple koro. staff ra nijeder user
name and pass diye login korbe. complex kono way ami cai na."*

**আগে কী ছিল:** প্রতিটা PC-র জন্য একবার-ব্যবহার্য enrollment code (H05) —
ড্যাশবোর্ডে বানাও, টুকে রাখো, ওই PC-তে গিয়ে লম্বা `msiexec` কমান্ডে বসাও,
২৪ ঘণ্টার মধ্যে শেষ করো।

⚠️⚠️ **এর সবচেয়ে খারাপ ব্যর্থতাটা নীরব:** কোন কোড কোন মেশিনে, সেটা
মানুষকে **হাতে মেলাতে** হতো। ভুল মিললে কোনো এরর আসত না, ইনস্টল সফলই হতো —
শুধু একজনের কাজের ঘণ্টা আরেকজনের নামে জমা হতো, আর ধরা পড়ত মাস শেষে
বেতনের হিসাব মেলাতে গিয়ে।

**এখন:** সার্ভারের ঠিকানা MSI-তে বেক করা যায়, তাই ইনস্টল = ডাবল-ক্লিক।
তারপর এজেন্ট স্টাফকে একটা জানালা দেখায়, আর সে **নিজের ইমেইল-পাসওয়ার্ড**
দিয়ে সাইন ইন করে (`POST /agent/enroll-login`)।

### কেন এটা কম নিরাপদ নয়, বরং বেশি নির্ভুল

| আপত্তি | জবাব |
|---|---|
| "এখন স্টাফ নিজেই ডিভাইস যোগ করতে পারে" | সে শুধু **নিজের ট্র্যাকিং যোগ** করতে পারে, বাদ দিতে পারে না। কেউ স্বেচ্ছায় নিজের উপর নজরদারি বসালে সেটা কোনো ক্ষতি নয় |
| "পাসওয়ার্ড এখন এজেন্টের ভেতর দিয়ে যায়" | ⚠️ যায়, কিন্তু **কোথাও জমা হয় না** — ওই কলটাতেই ডিভাইস টোকেনে বদলায়, আর ডিস্কে যায় শুধু টোকেন (DPAPI)। জানালায় সার্ভারের ঠিকানাটা দেখানো হয়, যাতে স্টাফ জানে পাসওয়ার্ড কোথায় যাচ্ছে |
| "brute force-এর নতুন দরজা" | ⭐ যাচাইটা **`AuthService.login()`-এই**, নকল করে লেখা হয়নি — তাই লগইনের throttle (I11), 2FA (I06) আর `audit_log` তিনটেই আপনাআপনি প্রযোজ্য। নিজে লিখলে এটাই হতো সবচেয়ে সহজ দরজা, কারণ এখানে cookie বা CSRF নেই |
| "ভুল মানুষ ভুল PC-তে সাইন ইন করতে পারে" | পারে — কিন্তু তখন সে **নিজের পাসওয়ার্ড দিয়ে নিজের নামে** করছে। আগের ব্যবস্থায় ভুলটা করত অ্যাডমিন, আর ভুক্তভোগী জানতও না |

### কোডের পথটা কেন রয়ে গেল

⚠️ **মুছে ফেলা হয়নি, ইচ্ছাকৃতভাবে।** রাতে দূর থেকে ১৫টা PC-তে বসাতে হলে
কারো কীবোর্ডে বসার সুযোগ থাকে না — তখন `ENROLLCODE=` লাগবেই। দুটো পথেরই
শেষ ধাপ **একটাই মেথড** (`EnrollmentService.bind()`), তাই দুটো আলাদা হয়ে
যাওয়ার সুযোগ নেই।

⚠️ owner ও manager-এর অ্যাকাউন্টে সাইন ইন **করা যায় না** (৪০৩) — তাঁদের
`users.employee_id` null, অর্থাৎ ঘণ্টা জমা করার জায়গাই নেই।

বিস্তারিত: [09 § ৩ড](09-Build-Log.md)।

### ⚠️ সাইন ইন **না** করলে কী হয় — ADR-024-এর অসমাপ্ত অর্ধেক

সিদ্ধান্তটা নেওয়ার সময় শুধু "সাইন ইন করলে কী হবে" ভাবা হয়েছিল। **না**
করলে কী হবে, সেটা কোথাও লেখা হয়নি — আর কোডে তখন উত্তরটা দাঁড়িয়েছিল
*"সবকিছু আগের মতোই চলবে"*: ঘণ্টা গোনা, ছবি তোলা, অ্যাপের হিসাব, সব।

**এখনকার নিয়ম:** সাইন ইন না হওয়া পর্যন্ত এজেন্ট **কিছুই** করে না —
কোনো সেগমেন্ট নয়, কোনো ছবি নয়, কোনো অ্যাপ-ব্যবহার নয়। tray-তে লাল
বিন্দু আর *"Not signed in — not counting hours"*।

⚠️⚠️ কেন এটা নিছক পরিপাটি করা নয়: সারিগুলো ডিভাইস-পরিচয় **ছাড়া** জমত,
আর স্টাফ সাইন ইন করামাত্র ডিভাইসটা তার নামে বাঁধা পড়ে সবগুলো তার খাতায়
চলে যেত। অর্থাৎ ADR-024-এর মূল প্রতিশ্রুতি — *"যে কীবোর্ডে বসে সে নিজেই
প্রমাণ করে সে কে"* — ঠিক সেখানেই ভাঙত।

⭐ নিয়মটা `TrackingGate` (Core)-এ, আর চারটে জায়গা সেটাই মানে।
বিস্তারিত: [09 § ৩প](09-Build-Log.md) · [G79](08-Gap-Analysis.md)।

### ⭐⭐ ডিভাইসের পরিচয় কী — *(সংশোধিত ১৫ আগস্ট)*

ADR-024 বলেছিল **কে** ডিভাইস বাঁধে (স্টাফ নিজে)। কিন্তু **ডিভাইসটা কী** —
সেটা কোথাও লেখা ছিল না; উত্তরটা বাস করত একটামাত্র জায়গায়, `devices` টেবিলের
`machine_guid` কলামের **UNIQUE** ইনডেক্সে। অর্থাৎ অলিখিত নিয়মটা দাঁড়িয়েছিল:

> **একটা মেশিন = একজন মানুষ।**

⚠️⚠️ অফিসে সেটা সত্যি নয়। দুজন স্টাফ একই PC-তে **আলাদা Windows অ্যাকাউন্টে**
বসেন, আর `HKLM\…\MachineGuid` মেশিনের — কার অ্যাকাউন্ট তাতে কিছুই আসে যায় না।
ফল: দ্বিতীয়জন সাইন ইন করলে প্রথমজনের সারিটাই তাঁর নামে চলে যেত। মাঠে যা দেখা
গেছে — Belal-এর PC হুট করে offline, আর স্টাফ পাতায় তিনি আবার
*"Ready to install"*।

**এখনকার পরিচয়:** `@@unique([hostname, windowsUsername])` — *মেশিন + যিনি
বসেছেন*। `machine_guid` কলামটা থাকছে (H04-এর rollout bucket ওটা দিয়েই গোনে),
কিন্তু তার UNIQUE তুলে দেওয়া হয়েছে (migration `20260815050000`)।

| পরিস্থিতি | আগে | এখন |
|---|---|---|
| এক PC, দুই Windows অ্যাকাউন্ট | একটাই সারি, নীরব হাতবদল | **দুটো সারি** |
| একই কর্মী আবার ইনস্টল করলেন | একই সারি হালনাগাদ | একই সারি হালনাগাদ |
| একই Windows অ্যাকাউন্টে অন্য কর্মী | নীরব হাতবদল | **৪০৯** — owner revoke করবেন |

⚠️ **আমার প্রথম রোগনির্ণয়টা ভুল ছিল, আর সেই ভুল ডিপ্লয়ও হয়েছিল।** হোস্টনেম
দুরকম দেখে ধরে নিয়েছিলাম PC-গুলো ডিস্ক-ইমেজ ক্লোন করা, আর সেই অনুমান ধরে
একটা গার্ড বসাই। প্রোডাকশনের লগ পরে বলে দেয় আসল কথাটা: *"Same hostname: two
people are signing in on one PC"* — অর্থাৎ গার্ডটাই তাঁদের রোলআউট আটকাচ্ছিল।
⭐ শিক্ষা: **অনুমান নয়, `audit_log` আর `events` টেবিল আগে পড়া** — সেখানে
ঘটনাটা লেখাই ছিল। পুরো গল্প [09 § ৩ঘ২](09-Build-Log.md) ·
[G132](08-Gap-Analysis.md)।

## ADR-026 · সিস্টেম কোথায় চলবে (O12) ✅ **আগে অফিসের PC, তারপর VPS**

**সিদ্ধান্ত আপনার** *(১৩ আগস্ট)* — *"VPS server e host korbo"*, আর তার
সাথেই: *"apatoto office er pc te thak. office er pc te 2-3 din check kore
VPS e host korbo."* তারপর VPS হাতে পেয়ে: *"ami hub.oxeio.com e er
monitoring system ta install korte cai"*।

⭐ **ঠিকানা চূড়ান্ত: `hub.oxeio.com`** — `build.ps1`-এর ডিফল্ট এখন এটাই,
আর MSI ০.৩.৭-এ বেক করা।

⚠️ **সাবডোমেইন, apex নয়।** `oxeio.com` কোম্পানির নিজের সাইট হতে পারে;
apex-এ A রেকর্ড বদলালে ওটা ভেঙে যেত। ⭐ DNS যেখানেই থাকুক (VPS
প্রোভাইডারে না হলেও) — **nameserver বদলানোর দরকার নেই**, শুধু একটা
`A` রেকর্ড: `hub` → VPS-এর IP।

### ⭐ দুই ধাপে — আর ধাপটা কাল্পনিক নয়

| ধাপ | কোথায় | TLS | `SERVERURL` |
|---|---|---|---|
| **১ · এখন** (২–৩ দিন) | অফিসের PC | self-signed (§ ৩ক) | `https://oxeio.office.local` |
| **২ · তারপর** | VPS | Let's Encrypt (§ ৩) | আসল ডোমেইন |

⭐ **কেন এটা সস্তা:** ধাপ ১-এ যা শেখা যাবে (এজেন্ট ঠিকমতো enroll করছে
কি না, ঘণ্টা মিলছে কি না, স্ক্রিনশট আসছে কি না) তার কোনোটাই হোস্টিংয়ের
উপর নির্ভর করে না। অথচ ভুল থাকলে সেটা LAN-এ ধরা পড়া অনেক সহজ — নেটওয়ার্ক,
সার্ট, ফায়ারওয়াল, কিছুই পথে দাঁড়ায় না।

### ⭐⭐ ঠিকানা বদলাতে ১৫টা PC-তে ফিরে যেতে হবে না

⚠️ প্রথমে মনে হয় MSI-তে ঠিকানা "বেক" করা মানে সেটা চিরকালের জন্য গাঁথা।
**তা নয়** — এজেন্ট ঠিকানা পড়ে রেজিস্ট্রি থেকে
(`HKLM\SOFTWARE\oXeio\Agent` → `ServerUrl`), আর MSI শুধু ইনস্টলের সময়
ওই মানটা **লিখে দেয়**।

তাই ধাপ ২-এ প্রতিটা PC-তে যা লাগবে:

```powershell
Set-ItemProperty 'HKLM:\SOFTWARE\oXeio\Agent' ServerUrl 'https://<নতুন-ডোমেইন>'
Stop-Process -Name oXeio.Agent -Force     # watchdog ৩০ সে.-এ ফিরিয়ে আনে
```

⭐ **কিউয়ে জমা ডেটাও হারায় না** — outbox লোকাল SQLite-এ, নতুন সার্ভারে
গিয়েই আপলোড হবে। ⚠️ তবে ডিভাইস টোকেন পুরোনো সার্ভারের, তাই নতুন সার্ভারে
আবার enroll করতে হবে (`device.dat` মুছে) — **অথবা** পুরোনো সার্ভারের
ডাটাবেস ডাম্প VPS-এ restore করলে টোকেনও সাথে যায়, আর কিছুই করতে হয় না।

⭐ **দ্বিতীয় পথটাই সুপারিশ** — `pg_dump` restore করলে কর্মী, ডিভাইস,
ঘণ্টা, সব একসাথে যায়; ২–৩ দিনের ডেটাও থাকে। ব্যাকআপ ও restore আগেই
মাঠে যাচাই করা ([09 § ৩আ](09-Build-Log.md))।

⚠️ স্ক্রিনশটের ফাইলগুলো `pg_dump`-এ **নেই** — ওগুলো `STORAGE_ROOT`-এর
ফোল্ডারে। ডিভাইস টোকেন রাখতে চাইলে ওই ফোল্ডারটাও কপি করতে হবে, নইলে
গ্যালারিতে সারি থাকবে কিন্তু ছবি খুলবে না।

### ⚠️⚠️ যা এই সিদ্ধান্তের সাথে **অবশ্যই** বদলাতে হবে

| | কেন |
|---|---|
| `SERVERURL` | `oxeio.office.local` → আসল ডোমেইন। MSI-তে বেক হয়, তাই **সব PC-তে বসানোর আগে** ঠিক হওয়া চাই |
| TLS | self-signed-এর বদলে **Let's Encrypt** — পাবলিক ডোমেইনে বিনামূল্যে, আর ব্রাউজারে সতর্কতা আসে না |
| `SERVERPIN` | ⚠️⚠️ নিচের ফাঁদটা পড়ুন |
| ফায়ারওয়াল | এখনকার নিয়মগুলো LAN ধরে লেখা; API এখন পাবলিক ইন্টারনেটে |
| `deploy/README` § ০ | ডেটা আর অফিসের মেশিনে নেই |

### ⚠️⚠️ Let's Encrypt + পিনিং — তিন মাস পর সব বন্ধ হওয়ার ফাঁদ

I01-এর পিনিং **SPKI**-র হ্যাশ ধরে (পুরো সার্টের নয়)। LE সার্ট ৯০ দিনে
নবায়ন হয় — আর certbot ডিফল্টে **প্রতিবার নতুন কী** বানায়। নতুন কী মানে
নতুন SPKI, অর্থাৎ **১৫টা এজেন্ট একসাথে সংযোগ হারাবে**, ঠিক তিন মাস পর,
কোনো পূর্বাভাস ছাড়াই।

⭐ **সমাধান দুটো, দুটোই ব্যবহার করুন:**

1. `certbot renew --reuse-key` — কী এক থাকে, তাই SPKI-ও এক। পিন বদলাতেই হয় না।
2. ⚠️ তবু নবায়নের আগে **দুটো পিন** বসিয়ে রাখুন — `CertificatePin` একাধিক
   পিন মানে, আর ঠিক এই কারণেই মানে (I01-এর ডক দেখুন)। কী বদলাতে বাধ্য
   হলে (কী ফাঁস হলে) তখন ফ্লিট বাঁচে।

⚠️ **অথবা সহজতম পথ: পিনিং বন্ধ রাখুন।** পাবলিক CA-র সার্টে Windows-এর
নিজের যাচাইই যথেষ্ট শক্ত — পিনিং মূলত self-signed সার্টের জন্য দরকার ছিল,
যেখানে "যেকোনো সার্ট Windows মানলেই হলো" দুর্বল। `SERVERPIN` না দিলে
পিনিং এমনিতেই বন্ধ থাকে আর এজেন্ট লগে সেটা লিখে জানায়।

### VPS-এর মাপ — অনুমান নয়, মাপা সংখ্যা থেকে

সব হিসাবের ভিত্তি ১১ আগস্টের **আসল ক্যাপচার**: ১৯২০×১০৮০ WebP q70 →
**১২৩ KB ও ৯৯ KB**, থাম্বনেইল ~১০ KB। ৮ ঘণ্টা ACTIVE, ৫ মিনিটে একটা স্লট।

#### 💾 ডিস্ক — এটাই একমাত্র শক্ত সীমা

| স্টাফের মনিটর | প্রতি কর্মী/দিন | ১৫ জন · ৯০ দিন |
|---|---|---|
| ১টা করে | ~১১ MB | ~১৫ GB |
| **গড়ে ১.৫টা** | **~১৭ MB** | **~২২ GB** |
| সবার ২টা | ~২৩ MB | ~৩০ GB |

সাথে যোগ হবে — Postgres **~১ GB/বছর** (segment ও app_usage-ই বড় অংশ) ·
এনক্রিপটেড ব্যাকআপ ~২ GB · OS ও Docker ইমেজ ~১০ GB।

⭐ **মোট ~৩৫–৪৫ GB স্থায়ী দখল।**

⚠️⚠️ **৫০ GB নেবেন না।** চলবে, কিন্তু retention জব একদিন ব্যর্থ হলে বা
ছুটির দিনেও কেউ কাজ করলে ভরে যাবে — আর **ডিস্ক ভরলে Postgres লেখা বন্ধ
করে দেয়**, অর্থাৎ ১৫টা এজেন্টের ডেটাই আটকে যায়। ⭐ ৮০ GB-তে দ্বিগুণ
জায়গা থাকে, আর retention ১৮০ দিনে বাড়ালেও (~৪৫ GB ছবি) কুলিয়ে যায়।

#### 🧠 RAM — ৪ GB

Postgres ~১ GB · NestJS ~৪০০ MB · Caddy ~৫০ MB · OS ~৫০০ MB।
⚠️ ২ GB-তে সাধারণ সময়ে চলবে, কিন্তু রাত ২:৩০-এ `pg_dump` + এনক্রিপশন আর
১৫-মিনিটের rollup একসাথে পড়লে চাপে পড়বে।

#### ⚙️ CPU — ২ vCPU যথেষ্ট

⭐⭐ **থাম্বনেইল বানায় এজেন্ট, সার্ভার নয়** (`WebpEncoder.EncodeThumb`) —
তাই সার্ভারে ভারী ছবির কাজ নেই, শুধু বাইট ডিস্কে লেখা। এটা যাচাই করে
দেখা হয়েছে, কারণ ধরে নেওয়া হচ্ছিল সার্ভার রিসাইজ করে; করলে CPU-র চাহিদা
অনেক বেশি হতো। ভারী মুহূর্ত কেবল রাতের ব্যাকআপ আর Excel/PDF রিপোর্ট।

#### 🌐 ব্যান্ডউইথ — যেকোনো প্ল্যানেই যথেষ্ট

আপলোড **~৭.৫ GB/মাস** (inbound, প্রায় সব প্রোভাইডারে ফ্রি)। ছবি দেখা
outbound — দিনে ১০০টা ছবি দেখলেও মাসে ১ GB-র কম। সব প্ল্যানে ১–২ TB থাকে।

### ⭐ সুপারিশ: ২ vCPU · ৪ GB RAM · ৮০ GB SSD

মাসে মোটামুটি **$১২–২৪**। ⚠️ প্ল্যান বাছার সময় তিনটে জিনিস দেখবেন:

| | কেন |
|---|---|
| ডিস্ক আলাদা করে বাড়ানো যায় কি না | retention ৯০ → ১৮০ দিন করলে ছবি দ্বিগুণ। কিছু প্রোভাইডারে volume যোগ করা যায়, কিছুতে পুরো প্ল্যান বদলাতে হয় |
| স্ন্যাপশট/ব্যাকআপ সুবিধা | G39-এর অফসাইট ব্যাকআপের প্রশ্নটা এতে অনেকটাই মেটে |
| অবস্থান | সিঙ্গাপুর বা জার্মানি — ⚠️ ঢাকা থেকে যত কাছে, ড্যাশবোর্ডে ছবি খুলতে তত কম দেরি |

⚠️ ডিস্কের ৮০% ও ৯৫%-এ অ্যালার্ট আছে (G03) — VPS-এ ওটা এখন সত্যিই কাজে
লাগবে, কারণ অফিসের ১ TB NVMe-র মতো জায়গা আর নেই।

## ADR-025 · মাঝপথে যোগ দিলে বেতন ও টার্গেট (G37) ✅ **কর্মদিবস × ৮ ঘণ্টা**

**সিদ্ধান্ত আপনার** *(১২ আগস্ট)* — *"কেউ যদি ১০ তারিখ join করে বা মাসে ১৭
hours এর কাজ করে তাহলে সে only ওই ১৭ hours এ salary পাবে। … কেউ যদি ১৫
তারিখ join করে তাহলে only ১৫ দিনের salary পাবে। … holiday গুলা বাদ দিবে।
Daily 8 hours count করে salary set করবে।"*

✅ **কোডে বসেছে** *(১২ আগস্ট রাত)* — [09 § ৩ভ](09-Build-Log.md)।

### নিয়মটা

```
D = ওই মাসের কর্মদিবস        (সাপ্তাহিক ছুটি ও holidays টেবিল বাদে)
d = তার নিজের কর্মদিবস        (joined_on … left_on-এর ভেতরে যতগুলো পড়ে)

দৈনিক টার্গেট = monthly_target_hours ÷ expected_workdays  = ২০৮ ÷ ২৬ = ৮ ঘণ্টা
টার্গেট       = d × ৮ ঘণ্টা
প্রযোজ্য বেতন  = মাসিক বেতন × d ÷ D
```

### ⭐ "১৭ ঘণ্টার বেতন" অংশটা **ইতিমধ্যেই কাজ করে**

`payroll.math.ts` করে `প্রদেয় = বেতন − বেতন × ঘাটতি ÷ টার্গেট`, যা
বীজগণিতে **কাজ করা ঘণ্টা × ঘণ্টাপ্রতি হার**-এর সমান। বেতন ২০,০০০ ·
টার্গেট ২০৮ঘ · কাজ ১৭ঘ → প্রদেয় ১,৬৩৫; আর ১৭ × (২০০০০÷২০৮) = ১,৬৩৫।
তাই এই শর্তে **কোনো কোড বদলাবে না**। যা সত্যিই নেই তা হলো join/leave-এর
proration।

### ⚠️⚠️ বেতন আর টার্গেট — **দুটোই একসাথে** prorate করতে হবে

শুধু টার্গেট prorate করলে ঘণ্টার হার **দ্বিগুণ** হয়ে যেত: ১৩ কর্মদিবস ×
৮ = ১০৪ঘ, বেতন ২০,০০০ → হার ১৯২ টাকা/ঘণ্টা (হওয়ার কথা ৯৬)।

দুটোই করলে হার = (S·d/D) ÷ (d×৮) = **S ÷ (D×৮)** — অর্থাৎ যে ১৫ তারিখে
যোগ দিল আর যে পুরো মাস আছে, দুজনের ঘণ্টাপ্রতি হার **হুবহু এক**।

### পাঁচটা উপ-সিদ্ধান্ত

| প্রশ্ন | সিদ্ধান্ত |
|---|---|
| পুরো মাস কাজ করা কর্মীর টার্গেট? | **কর্মদিবস × ৮, কোনো সীমা নেই** — ফেব্রুয়ারি ১৯২ঘ, মার্চ/আগস্ট/ডিসেম্বর ২১৬ঘ। ঈদের ছুটিতে আরও কম |
| টার্গেটের বেশি কাজ করলে? | **prorated বেতনই সর্বোচ্চ** — OT-র ঘণ্টা দেখানো হয়, টাকা নয় (ADR-023 অপরিবর্তিত, O4 এখনো খোলা) |
| সাপ্তাহিক ছুটি? | **শুধু শুক্রবার** *(১২ আগস্ট নিশ্চিত: "৪ শুক্রবারের")* — সপ্তাহে ৬ কর্মদিবস × ৮ঘ = ৪৮ঘ |
| দিন ধরে কাটা, নাকি মাস ধরে? | **মাস ধরে** — সোম ৭ঘ + মঙ্গল ৯ঘ = কোনো কর্তন নয়। O8-এর সিদ্ধান্তই বহাল: দৈনিক ৮ ঘণ্টা শুধু **দেখানোর**, কাটার নয় |
| শুক্রবার/ছুটির দিনে কাজ করলে? | **ঘণ্টা পুরোপুরি গোনা হয়** — ওই দিনগুলো টার্গেটে যোগ হয় না, কিন্তু কাজ করলে জমা হয়। অর্থাৎ শুক্রবার একটা খাঁটি বোনাস-দিন |

### ⭐ মালিকের নিজের উদাহরণ *(১২ আগস্ট)*

> *"সারা সপ্তাহে ৮ ঘন্টার বদলে ৭ ঘন্টা করে কাজ করেছে। সপ্তাহ শেষে তার গ্যাপ
> দাঁড়ায় ৬ ঘন্টা। এখন সে যদি এর পরের যেকোন শুক্রবার ঐ ৬ ঘন্টা কাজ করে দেয়
> তাহলে তার ঐ ৬ ঘন্টা কর্তন করা হবে না। … গ্যাপ গুলা ঐ মাসের মধ্যে যেকোন
> সময় করে দিলেই সেটা আমরা মেনে নিব + কাউন্ট করব।"*

সেপ্টেম্বর ২০২৬ · ২৫ কর্মদিবস · টার্গেট ২০০ঘ · বেতন ৳১০,০০০ · হার ৳৫০/ঘ:

| | মোট | কর্তন | প্রদেয় |
|---|---|---|---|
| গ্যাপ না পূরণ করলে | ১৯৪ঘ | ৩০০ | ৳৯,৭০০ |
| **শুক্রবারে ৬ঘ করে দিলে** | ২০০ঘ | **০** | **৳১০,০০০** |
| শুক্রবারে ৪ঘ করলে | ১৯৮ঘ | ১০০ | ৳৯,৯০০ |

### ⚠️ "ঐ মাসের মধ্যে" — দুটো ফল

- **আগের মাসের গ্যাপ পরের মাসে পূরণ করা যায় না।** আগস্টের ৬ ঘণ্টা ২রা
  সেপ্টেম্বর করে দিলে আগস্টের কর্তনটা বসেই যাবে — ওই মাস ৩১ তারিখে বন্ধ।
- **বাড়তি ঘণ্টাও পরের মাসে যায় না।** কেউ ২২০ঘ করলে বাড়তি ১২ঘ সেপ্টেম্বরে
  যোগ হবে না।

⭐ প্রতিটা মাস আলাদা করে মিটে যায় — মালিকের *"চলমান গ্যাপ ঐ মাসেই ফিলাপ"*
কথাটার সাথে এটাই মেলে, আর `monthly_summary`-র নকশাও তাই।

### ⚠️ ঘণ্টাপ্রতি হার প্রতি মাসে বদলাবে

একই ৳১০,০০০ বেতনে — ফেব্রুয়ারি (২৪ দিন) ৳৫২.০৮/ঘ · সেপ্টেম্বর (২৬ দিন)
৳৪৮.০৮/ঘ · আগস্ট (২৭ দিন) ৳৪৬.৩০/ঘ।

গাণিতিকভাবে অনিবার্য: "পুরো মাস কাজ = পুরো বেতন" **আর** "টার্গেট =
কর্মদিবস × ৮" — দুটো একসাথে মানলে হারকে ওঠানামা করতেই হয়। পে-রোল শিটে
হারটা দেখা যায়, তাই আগে থেকে জানা থাকা দরকার।

⚠️ "৮ ঘণ্টা" **হার্ডকোড হবে না** — পলিসির দুটো কলাম থেকে ভাগ করে বের হবে
(`monthly_target_hours ÷ expected_workdays`)। এখন ঠিক ৮ আসে, আর ভবিষ্যতে
চুক্তি বদলালে নিয়মটাও সাথে বদলায়। কোনো migration লাগে না।

### ⚠️ যা এমনিতেই বদলে যাবে

- **সবার টার্গেট** ফ্ল্যাট ২০৮ থেকে কর্মদিবস×৮ হবে
- **পুরোনো মাসের সংখ্যাও** পরের rollup-এ নতুন নিয়মে বসবে (জব ১৫ মিনিট পরপর চলে)
- `monthly_summary.expected_workdays`-এর **মানে বদলাবে** — "মাসের কর্মদিবস" → "তার কর্মদিবস"

✅ **শেষ উত্তরটাও এসেছে (১২ আগস্ট)** — [O10](#-এখনো-খোলা-সিদ্ধান্ত): নিয়মটা
**সবখানে** বসবে, পুরোনো মাস সহ। (O9 ও O11-ও ১২ আগস্ট নিষ্পত্তি হয়েছে।)

## ADR-027 · ম্যানেজারের অ্যাক্সেস ✅ **Staff · Holidays · Categories**

**সিদ্ধান্ত আপনার** *(১৫ আগস্ট)* — *"ami cai manager staff, holyday,
catagory er access pabe"*। দুটো খুঁটিনাটিও আপনারই বাছা: স্টাফে **যোগ ও
এডিট, বেতন নয়**; ছুটি ও ক্যাটাগরিতে **দেখা ও বদলানো দুটোই**।

**আগে কী ছিল:** ম্যানেজার সব **দেখতে** পেতেন, কিছুই **বদলাতে** পারতেন না।
বাস্তবে তার মানে দাঁড়াত — নতুন কর্মী যোগ করা, ছুটির তারিখ বসানো বা নতুন
ডোমেইন শ্রেণিভুক্ত করা, প্রতিটার জন্য মালিককে ডাকতে হতো। এগুলো রোজকার কাজ,
আর রোলআউটের দিনগুলোয় ওটাই ছিল সবচেয়ে বড় জট।

### যা দেওয়া হলো, আর যা হলো না

| | কেন |
|---|---|
| ✅ কর্মী যোগ ও এডিট | রোজকার কাজ। ভুল হলে audit-এ নাম ধরে লেখা থাকে |
| ✅ ছুটি | ⚠️ তারিখটা টাকা নাড়ায় (`d ÷ D`), কিন্তু বন্ধ মাস (R1) ছোঁয়া যায় না আর প্রতিটা বদল audit-এ |
| ✅ ক্যাটাগরি | নতুন ডোমেইন শ্রেণিভুক্ত করতে owner-কে ডাকতে হলে "কত শতাংশ অচেনা" সংখ্যাটা বাড়তেই থাকত |
| ❌ **বেতন** | [ADR-023](#adr-023--বেতন-ও-ঘাটতির-টাকা--রাখা-হবে-শুধু-owner-দেখবেন) — দেখাও না, বসানোও না |
| ❌ কর্মী নিষ্ক্রিয় করা, portal account, পাসওয়ার্ড রিসেট | মানুষটার সিস্টেমে থাকা-না-থাকার সিদ্ধান্ত |
| ❌ Work policy · ছুটির খাতা · মাস বন্ধ · এজেন্ট আপডেট | সবগুলোই হয় টাকার ভিত্তি, নয়তো প্রতিটা PC-র আচরণ বদলায় |
| ❌ Audit log · অ্যালার্ট · ডিভাইস | "কে কার স্ক্রিনশট দেখেছে" ম্যানেজারের পড়ার জিনিস নয় |

### ⚠️⚠️ যে জায়গাটা সহজে ফাঁক থেকে যেত

শুধু `@Roles`-এ `manager` জুড়ে দিলে **বেতনের লেখার দিকটা খোলা থেকে যেত** —
কারণ `redact.ts` কেবল উত্তর ছাঁকে। সেই পাহারাটা আলাদা করে বসাতে হয়েছে,
বিস্তারিত ADR-023-এ।

### ⚠️ এক অধিকার = তিন জায়গা (ওয়েবে)

নেভ (`Layout`) · রুট (`App.tsx`) · পর্দা (`SettingsPage`)। প্রথম দফায় তিনটের
**দুটো** খোলা হয়েছিল, ফলে ম্যানেজার নেভে Settings দেখতেন আর চাপলে
"Not found" পেতেন — মাঠে ধরা পড়েছে ডিপ্লয়ের কয়েক মিনিটের মধ্যে
([G134](08-Gap-Analysis.md))। শর্তটা এখন নাম পেয়েছে (`mayOpenSettings`)।

⭐ সার্ভারে role শিথিল হয়েছে **মেথডে, ক্লাসে নয়** — তাই একই কন্ট্রোলারের
বাকি রুট আর ভবিষ্যতের নতুন রুট আপনাআপনি owner-only থাকে। ঠিক উল্টো যুক্তিতে
holidays ও categories-এ **ক্লাস-লেভেলে**: ওখানে গোটা কন্ট্রোলারই ম্যানেজারের।

[07 § ৪.৩](07-Technical-Spec.md)।

## ADR-028 · সিকিউরিটি মানি (জামানত) ✅ **প্রতি মাসে ৫০০, খাতায় লেখা থাকে**

**সিদ্ধান্ত আপনার** *(১৫ আগস্ট)* — *"আমরা ইদানিং সকল স্টাফদের থেকে
প্রতিমাসের সেলারি থেকে ৫০০ টাকা কেটে রাখছি, সিকিউরিটি মানি হিসাবে… এই
প্রতি মাসে ৫০০ করে টাকা সে আবার ব্যাক পাবে যখন জব ছেড়ে দিবে বা রিজাইন
করবে… ৩০ দিন আগে না জানালে সে ঐ জমানো টাকা এবিল করতে পারবেনা।"*

### ⭐⭐ মূল সিদ্ধান্তটা: খাতা **লিখে রাখা হয়**, গোনা হয় না

সবচেয়ে সহজ বাস্তবায়ন হতো "মাস গুনে × ৫০০"। সেটাই বাদ দেওয়া হয়েছে।

```
জমা = (কত মাস) × (আজকের অঙ্ক)        ← বাদ
জমা = প্রতিটা মাসের নিজের কিস্তির যোগ  ← এটাই
```

⚠️⚠️ কারণটা টাকার: অঙ্কটা কাল ৬০০ হলে প্রথম হিসাবে **গত ছ-মাসের জমাও
পিছন ফিরে বেড়ে যেত** — খাতা এমন টাকা দাবি করত যা কর্মী কোনোদিন দেননি,
আর উল্টোটা (অঙ্ক কমালে) নীরবে টাকা উবে যেত। জমা টাকা একটা **ঘটনার
ইতিহাস**, আজকের নিয়মের ফল নয়। তাই `security_deposits`-এর প্রতিটা সারিতে
ওই মাসের অঙ্কটা নিজের ঘরে লেখা থাকে।

### ⚠️ কিস্তি বসে অলসভাবে, cron-এ নয়

খাতা যে-ই খোলেন — মালিকের পর্দা, পে-রোলের শিট, বা কর্মীর নিজের পাতা —
তখনই আজকের মাস পর্যন্ত পূর্ণ হয়ে যায় (`ensureLedger`, idempotent)।

⭐ cron হলে সার্ভার এক দিন বন্ধ থাকলেই একটা মাস নীরবে বাদ পড়ত, আর কেউ
টের পেত না — মাস শেষে বেতনের সময় ছাড়া। এই সিস্টেমে নীরব ব্যর্থতাই
সবচেয়ে বড় শত্রু, আর টাকার হিসাবে তো বটেই।

### ⚠️⚠️ ফেরতের সিদ্ধান্ত স্বয়ংক্রিয় নয় — আর সেটাই মালিকের পছন্দ

সিস্টেম **হিসাব** দেয়: কত দিনের নোটিশ হয়েছে, নিয়ম কত দিনের, কত জমেছে।
**সিদ্ধান্ত** মালিকের, আর যা করলেন সেটা `deposit_settlements`-এ নিয়মসহ
লেখা থাকে (`notice_days_given` বনাম `notice_days_rule`)।

⭐ ব্যতিক্রম সবসময়ই থাকে — হাসপাতাল, পারিবারিক কারণ — আর সেগুলো কোনো
`if`-এ ধরা যায় না। স্বয়ংক্রিয় করলে মালিককে নিয়মটা **ভাঙতে** হতো, অথচ
ভাঙার কোনো পথ থাকত না। ⚠️ তারিখ না জানা থাকলে "নিয়ম মেলেনি" ধরা হয় —
"জানি না"-কে "হ্যাঁ" ধরে নেওয়া মানে নীরবে নিয়মটা মাফ করে দেওয়া।

### কে দেখেন

| | |
|---|---|
| owner | সবার জমা, নিয়ম বদলানো, নিষ্পত্তি — সাইডবারে **Deposits** (`/deposits`) |
| ⚠️ manager | **কিছুই না।** জামানত সরাসরি বেতনের অংশ (ADR-023 · ADR-027) |
| ⭐ স্টাফ | **নিজের** মোট ও মাস-ধরে তালিকা, নিজের পাতায় (`/me`) |

⭐ স্টাফের দেখাটা ADR-023 ভাঙে না: অঙ্কটা **তাঁর নিজের টাকা**, বেতনের
হিসাব নয়, আর এটা থেকে কারো বেতন বের করা যায় না।

### পে-রোলে

`payable` (ঘণ্টার হিসাবে প্রাপ্য) আর `netPayable` (এই মাসে হাতে যাবে) —
**দুটোই** শিটে থাকে। জামানত বেতন কমায় না, শুধু জমা থাকে; একটাই সংখ্যা
দেখালে ওই পার্থক্যটা হারাত, আর ছাড়ার সময় ফেরতের হিসাব ব্যাখ্যাই করা যেত না।

⚠️ কারো প্রদেয় কিস্তির চেয়ে কম হলে (পুরো মাস অনুপস্থিত) নিট শূন্যে থামে,
আর নামটা শিটে আলাদা করে বলা হয় — নীরবে থামালে খাতায় জমা দেখাত অথচ
টাকাটা কোনোদিন কাটাই যেত না।

পুরো গল্প [10 § R21](10-Roadmap.md)।

## ADR-029 · টেলিগ্রামে কখন খবর যাবে ⛔ **বাতিল — বিকল্প (গ)-ই ঠিক ছিল**

*১৭ আগস্ট ২০২৬ · ⛔ বাতিল ১৮ আগস্ট ২০২৬ → [ADR-031](#adr-031)*

> ## ⛔ এই সিদ্ধান্তটা ২৪ ঘণ্টাও টেকেনি
>
> ঘণ্টার স্ন্যাপশট **তুলে দেওয়া হয়েছে**, আর নিচের টেবিলের যে সারিটাকে
> তখন খুব সংযত মনে হয়েছিল — **(গ) শুধু দৈনিক ডাইজেস্ট, দিনে ১** — সেটাই
> শেষ পর্যন্ত সঠিক উত্তর। কেন, তা [ADR-031](#adr-031)-এ।
>
> ⚠️⚠️ **যে ভুলটা এখানে হয়েছিল:** হিসাবটা করা হয়েছিল **শুধু স্ন্যাপশট
> নিয়ে** (দিনে ৮), অথচ ওই একই চ্যাটে `agent_down` অ্যালার্টও যাচ্ছিল —
> মাঠে মেপে **দিনে ৩৯টা**। অর্থাৎ যে বন্যাটা ঠেকাতে (খ) বাছা হলো,
> সেটা পাশের দরজা দিয়ে ইতিমধ্যেই ঢুকে বসে ছিল, আর সেই দরজাটা এই
> ADR গুনতেই ভুলে গিয়েছিল।

**প্রশ্ন:** মালিক চেয়েছিলেন তিনটে জিনিস — দৈনিক রিপোর্ট, কে কাজ করছে কে
করছে না, আর **কেউ ১০ মিনিটের বেশি idle থাকলেই খবর**।

### বিকল্পগুলো

| | কী | দিনে কত বার্তা |
|---|---|---|
| ক | প্রতি বিরতিতে অ্যালার্ট (মালিকের চাওয়া) | **৬০–১৮০** |
| খ | ⭐ ঘণ্টায় একটা স্ন্যাপশট | **৮** |
| গ | শুধু দৈনিক ডাইজেস্ট | ১ |

⚠️⚠️ হিসাবটা সরল: ১২ জন × দিনে ৫–১৫টা স্বাভাবিক বিরতি (চা, দুপুরের খাবার,
বাথরুম, ফোন, মিটিং, লম্বা নথি পড়া)। আর পরিণতিটা এই কোডবেসেই আগে থেকে লেখা
ছিল, `THROTTLE_HOURS`-এর ডকে:

> *"তারপর কেউ আর কোনো অ্যালার্ট পড়ত না, অর্থাৎ সত্যিকারের সমস্যাটাও চোখ
> এড়িয়ে যেত।"*

⚠️ আর শুধু শব্দ নয়, **অন্যায্যও**: মিটিংয়ে বসা বা স্পেক পড়া মানুষ এই মাপে
"idle", অথচ তিনি কাজই করছেন।

**সিদ্ধান্ত (খ)** — তিনটে বিকল্প সংখ্যাসহ দেখানোর পর মালিক নিজেই বেছেছেন।

⭐ বার্তাটা পড়ার যোগ্য রাখতে তিনটে নিয়ম: কাজ করা মানুষের **নাম লেখা হয় না**
শুধু গোনা · idle-এর সাথে **আজকের ঘণ্টা** (নইলে মনে হতো তিনি কিছুই করেননি) ·
রাতে পাঠানো হয় না ("Working now: 0/12" ভোর ২টায় কেবল শব্দ)।

> ⭐⭐ **ব্যবহারকারী যা চান আর যা দরকার — তফাতটা বলা আমার কাজ, কিন্তু
> সিদ্ধান্তটা তাঁর।**

## ADR-030 · লাইভ বোর্ডের স্ট্যাটাস ✅ **চারটে থেকে তিনটে**

*১৭ আগস্ট ২০২৬*

**প্রশ্ন:** 🔴 `agent_down` কি বোর্ডে থাকবে?

### কেন উঠে গেল

নিয়মটা **দুবার** লেখা হয়েছে, আর দুবারই মাঠে ভেঙেছে:

| চেষ্টা | নিয়ম | কী হলো |
|---|---|---|
| ১ | `> ৬০০ সে.` চুপ → 🔴 | ১৫ আগস্ট সন্ধ্যায় `Agent down 12 · Offline 0` — অফিস ছুটি হয়েছিল |
| ২ | শেষ কথা `active` → 🔴 | ১৭ আগস্ট বেলাল লাল — তিনি কাজ করতে করতে PC বন্ধ করে বাড়ি গিয়েছিলেন |

⚠️⚠️ কারণটা **কাঠামোগত**, নিয়ম লেখার দক্ষতার নয়: বিদায়ী ইভেন্টটা
(shutdown/logoff) এজেন্ট **ডিস্কে** লিখে রাখে আর পাঠায় পরের বার চালু হলে —
কারণ বন্ধ হওয়ার সময় হাতে মাত্র ৪ সেকেন্ড, নেটওয়ার্ক কল করা যায় না। অর্থাৎ
বোর্ডের কাছে ওই মুহূর্তে তথ্যটা **থাকেই না**।

> ⭐⭐⭐ **যে প্রশ্নের উত্তর জানা নেই, তার উত্তর অনুমান করে লাল রঙে লেখা
> সবচেয়ে খারাপ পথ** — লাল নিশ্চয়তার ভান করে, আর ভান ভাঙলে লাল রঙের মানেই
> হারিয়ে যায়।

**সিদ্ধান্ত:** `LiveStatus` = `active | idle | offline`। বোর্ড এখন শুধু
**কর্মীর** কথা বলে, যন্ত্রের নয়।

⭐ আসল ফল্ট হারায়নি — `AgentDownCheck` (G01) প্রতি ৫ মিনিটে চলে, বিদায়ী
ইভেন্ট দেখে, `isExpectedSilence()` দিয়ে ছাঁকে, আর **অ্যালার্ট** তোলে,
যেখানে ব্যাখ্যা আঁটে: *"no shutdown event arrived either"*।

⚠️ দামটা কম ছিল না: ওই ভুল লাল দেখে একটা গোটা রিলিজ থামানো হয়েছিল আর
কল্পিত একটা বাগের পেছনে সময় গেছে (09 § ৩৩)।

⭐ `agent_down` **অ্যালার্টের টাইপ** ও **ঘণ্টা-সংশোধনের কারণ** হিসেবে থাকছে —
ওখানে কথাটা সৎ, কারণ প্রমাণ আছে।

## ADR-031 · টেলিগ্রামে রোজ কী যাবে ✅ **দিনে একটা রিপোর্ট, আর কিছু নয়**

*১৮ আগস্ট ২০২৬*

**প্রশ্ন:** মালিক টেলিগ্রামের স্ক্রিনশট পাঠিয়ে লিখলেন —

> *"ami ei type er alart gula chaina. ami chai deily report type er.
> jemon ke koto hours kaj korlo. k target hit korlo. ei taiper info
> kintu organized way te."*

### ⚠️⚠️ আগে সংখ্যাটা — অনুমান নয়, মাঠে গোনা

| কী যাচ্ছিল | দিনে | সপ্তাহে |
|---|---:|---:|
| `agent_down` — "Agent silent — DESKTOP-…" | **৩৯** | ১৬৮ |
| ঘণ্টার স্ন্যাপশট — "Working now: 9/13" | **১১** | ৭৭ |
| **দৈনিক রিপোর্ট** | **১** | ৭ |

⭐ অর্থাৎ **দিনে ~৫০টা বার্তার নিচে একটা রিপোর্ট চাপা পড়ে ছিল** — আর ওই
রিপোর্টটাই মালিক আসলে চেয়েছিলেন, শুরু থেকেই।

### সিদ্ধান্ত

**১· ঘণ্টার স্ন্যাপশট তুলে দেওয়া হলো** ([ADR-029](#adr-029) বাতিল)।
⭐ "এখন কে কাজ করছে" প্রশ্নের উত্তর Live Board-এ **সবসময়** আছে; ওটা ঠেলে
পাঠানোর জিনিস ছিল না।

**২· `agent_down` টেলিগ্রামে আর যাবে না** (`TELEGRAM_MUTED_TYPES`)।
⚠️⚠️ **অ্যালার্টটা মুছে ফেলা হয়নি** — এটা কেবল একটা **চ্যানেল** ফিল্টার।
সারি তৈরি হয়, ইমেইলে যায়, Alerts পাতায় ওঠে, এজেন্ট ফিরলে নিজে থেকে
বন্ধও হয়। ⭐ ফোনে ওটা দিনে একবার, রিপোর্টের শেষে **এক লাইনে**:
*"৩টা PC আজ চুপ ছিল — Alerts পাতা বলবে কোনগুলো"*।

**৩· রিপোর্টটা টেলিগ্রামের নিজের চেহারা পেল।** আগে ইমেইলের বডি হুবহু যেত,
শেষে আট লাইনের *"How to read these numbers"* সহ। এখন দল করে সাজানো:
টার্গেট ছুঁয়েছেন → ছোঁননি → আজ কিছুই করেননি → আজ ছুটি → মাসে পিছিয়ে।
⚠️ ইমেইলটা **অপরিবর্তিত** — ওখানে বিস্তারিত ব্যাখ্যাটা ঠিক আছে; আর
সংখ্যা দুটোই একই `Digest` থেকে, তাই কোনোদিন দু-রকম কথা বলবে না।

### ⚠️ যেটা ইচ্ছাকৃতভাবে করা হয়নি

**ঘণ্টা ধরে সাজানো।** সবাইকে ঘণ্টার ক্রমে বসালে বার্তাটা রোজ সন্ধ্যায়
একটা **লিডারবোর্ড** হয়ে উঠত — README-র "কখনোই নয়" তালিকায় ওটা আছে।
প্রতিটা দলের ভেতরে ক্রম **কর্মী-কোড ধরে**।

**ছুটির লোকজন বাদ দেওয়া।** তাঁদের নিয়ে করণীয় নেই, কিন্তু নাম না লিখলে
**সংখ্যাগুলো মিলত না** (উপরে ১৩ জন, নিচে ১১টা নাম), আর ওই ফাঁকটা দেখতে
হুবহু "এজেন্ট কাজ করছে না"-র মতো লাগত।

### ⭐ শিক্ষা

একটা চ্যানেলের **মোট** বার্তা গোনা হয়নি — গোনা হয়েছিল কেবল নতুন যোগ হওয়া
জিনিসটার বার্তা। ⚠️ যে-কোনো নতুন নোটিফিকেশন যোগ করার আগে প্রশ্নটা হওয়া
উচিত *"এই চ্যাটে **মোট** কতটা যাচ্ছে?"* — *"আমারটা কতটা যোগ করছে?"* নয়।

## ADR-032 · স্টাফের হাতে বোতাম ✅ **নিয়মটা সংকুচিত, বাতিল নয়**

*২২ আগস্ট ২০২৬*

**প্রশ্ন:** ডিজাইন-টার্গেটের ব্যবস্থায় ডিজাইনার একটা টার্গেট বেছে নেন ও
দরকারে বাদ দেন। কিন্তু ডকে **দুই জায়গায়** লেখা আছে —

> *"স্টাফের চাপার মতো কোনো বাটনই নেই"* — [04-Features](04-Features.md),
> [08-Gap-Analysis](08-Gap-Analysis.md)

### ⚠️⚠️ আগে দেখা দরকার নিয়মটা **কেন** ছিল

মূল কারণ **ঘণ্টার সততা**। tray-তে pause/break বোতাম থাকলে মাপা সময় আর
বাস্তব সময় আলাদা হয়ে যেত, আর ২০৮ ঘণ্টার মানেই থাকত না — কারণ তখন
সংখ্যাটা "কী ঘটেছে" নয়, "কে কী ঘোষণা করেছে"।

⭐ **Skip ওই ঝুঁকির কিছুই বহন করে না:** ঘণ্টা ছোঁয় না, ডিজাইনের সংখ্যা
ছোঁয় না, টার্গেট বাড়ায়-কমায় না। ওটা একটা **কাজের সিদ্ধান্ত** — "এই
পণ্যটা নিয়ে কাজ করার মতো নয়" — আর সে সিদ্ধান্ত ডিজাইনারেরই।

### সিদ্ধান্ত

**নিয়মটা এভাবে সংকুচিত হলো:** স্টাফের হাতে এমন কোনো বোতাম থাকবে না
**যা মাপা সংখ্যাকে বদলায়**।

| বোতাম | রায় | কেন |
|---|---|---|
| Pause / Break / Meeting | ⛔ কখনো নয় | সরাসরি ঘণ্টা বদলায় |
| **Done** (টার্গেট শেষ) | ✅ **২৩ আগস্ট বসানো হলো** (`Complete`) | ২২ আগস্টে ছিল না — সংখ্যাটা স্বেচ্ছা-ঘোষণা হয়ে যেত, তাই ফাইলের নাম থেকেই ধরা হতো। ⚠️ কিন্তু ফাইলের নাম যা বলে সেটা **"শুরু"**, "শেষ" নয় — তাই শেষ হওয়া এখন ডিজাইনার নিজে বলেন (`POST /targets/:id/done`, [09 § ৩ম৪](09-Build-Log.md))। ⚠️⚠️ **ঘণ্টা** এখনো কোনো বোতাম ছোঁয় না; তবে ডিজাইনের গোনা ২৩ আগস্ট বিকেল থেকে Live Board · Reports · ডাইজেস্টে এই বোতাম থেকেই আসে ([ADR-037](#adr-037--ডিজাইন-গোনা--কেবল-complete-খোলা-নয়)) |
| **Skip** (টার্গেট বাদ) | ✅ আছে | কোনো সংখ্যা ছোঁয় না; কাজের সিদ্ধান্ত |
| **Copy** (নম্বর কপি) | ✅ আছে | নিছক সুবিধা |

⚠️ **পরের বার এই লাইনটা টানার সময় প্রশ্নটা হবে:** *"এই বোতাম চাপলে কি
কোনো মাপা সংখ্যা বদলায়?"* — "স্টাফ চাপছেন কি না" নয়।

## ADR-033 · প্রথম লগইনে বাধ্যতামূলক পাসওয়ার্ড বদল ✅ **মালিক নিজে বসালে নয়**

*২৩ আগস্ট ২০২৬*

**প্রশ্ন:** মালিক পর্দার ছবি পাঠিয়ে লিখলেন *"Pass change must korte hobe
eita korona."* — মাঠে **১২ জনের ৯ জনই** ওই পর্দায় আটকে ছিলেন।

### ⚠️⚠️ শুধু ধাপটা তুলে দিলে ফল হতো উল্টো

অ্যাকাউন্ট বানালে সিস্টেম **১৪ অক্ষরের এলোমেলো** পাসওয়ার্ড বানায়
(`kQ7#mZ2vX9pL4t` ধাঁচের), একবার মালিককে দেখায়, তিনি কর্মীকে দেন।

⭐ বাধ্যতামূলক বদলটাই ছিল ওই এলোমেলো স্ট্রিং থেকে বেরোনোর **একমাত্র পথ**।
ধাপটা তুলে দিলে কর্মী ওটাই চিরকাল বয়ে বেড়াতেন — মনে রাখতে না পেরে কাগজে
লিখে রাখতেন, যা আগের চেয়েও খারাপ।

### বিকল্পগুলো

| | কী | রায় |
|---|---|---|
| ক | শুধু বাধ্যতামূলক ধাপ তুলে দেওয়া | ⚠️ কর্মী এলোমেলো স্ট্রিং নিয়ে থাকতেন |
| **খ** | ⭐ **মালিক নিজে পাসওয়ার্ড বসাবেন**, তখন বদল বাধ্যতামূলক নয় | ✅ মালিকের বাছাই |
| গ | সবার জন্য একটাই পাসওয়ার্ড | ⛔ তখন কে কার অ্যাকাউন্টে কী করল বলা যেত না |

**সিদ্ধান্ত (খ)।**

> ## ⚠️⚠️ সংশোধন — ২৩ আগস্ট, একই দিনে
>
> প্রথমে লেখা হয়েছিল: *"পুরোনো পথটা মুছে ফেলা হয়নি — পাসওয়ার্ডের ঘরটা
> খালি রাখলে আগের আচরণই চলে।"* যুক্তি ছিল নিরাপত্তার জাল না ছেঁড়া।
>
> **মাঠে ফল:** মালিক পরদিনই আবার ওই দেয়ালে আটকালেন — `Reset` চেপে,
> ঘরটা খালি রেখে (audit: ০৮-২২ ০৭:৪৯)। ⭐ **আধা-মানা সিদ্ধান্ত মানে
> অর্ধেক সময় পুরোনো আচরণই ফিরে আসা।**
>
> ⭐ তাই এখন **কখনোই বাধ্যতামূলক নয়** — create ও reset দুটোতেই
> `mustChangePw: false`। পাসওয়ার্ড না দিলে এলোমেলো একটা বানানো হয়
> (একবার দেখানো হয়), কিন্তু বদলাতে বলা হয় না।
>
> ⚠️ **শিক্ষা:** মালিক যখন একটা আচরণ বন্ধ করতে বলেন, "কেবল এই পথে বন্ধ"
> রাখাটা সমাধান নয় — বাকি পথটা দিয়েই তিনি আবার ওখানে পৌঁছবেন।

### ⭐ কেন দুটো পথই রাখা হলো

ওই ধাপটার আসল উদ্দেশ্য ছিল একটাই: **মালিকের জানা পাসওয়ার্ড যেন চিরকাল
না থাকে**, যাতে কর্মীর অ্যাকাউন্টে কী ঘটল তার দায় শুধু তাঁরই থাকে।

মালিক নিজে বসালে সেই সুরক্ষাটা তিনি **জেনেবুঝে** ছাড়ছেন, আর ১৩ জনের
অফিসে সেটা যুক্তিসঙ্গত। ⚠️ কিন্তু ভবিষ্যতে কোনো স্ক্রিপ্ট বা নতুন পথ
পাসওয়ার্ড না দিয়ে অ্যাকাউন্ট বানালে **নিরাপদ আচরণটাই ডিফল্ট থাকা
উচিত** — নীরবে দুর্বল হয়ে যাওয়া নয়।

⚠️ **যা মালিকের জানা দরকার:** এখন তিনি সবার পাসওয়ার্ড জানেন। audit log
এখনো বলে *কোন অ্যাকাউন্ট* থেকে কী হলো, কিন্তু *কে বসেছিলেন* সেটা আর
পাসওয়ার্ড দিয়ে প্রমাণ হয় না। ⭐ কর্মী চাইলে Security পাতায় নিজেই
বদলে নিতে পারেন, আর তখন সুরক্ষাটা ফিরে আসে।

## ADR-034 · USA থেকে BDIX-এ সার্ভার সরানো ✅ **ডোমেইন একই, গোপন মান একই**

| `SCREENSHOT_URL_SECRET` | ১৬,২৪২টা স্ক্রিনশটের স্বাক্ষরিত লিঙ্ক অচল |
| `JWT_SECRET` | সবার সেশন ভাঙত |

⭐ তাই পথটা ছিল **`/opt/oxeio` পুরোটা rsync** — কোড, `.env`, `.data` একসাথে।
`.env`-এর একটা মানও বদলাতে হয়নি, কারণ ডোমেইন (`hub.oxeio.com`) একই থেকেছে
আর `TLS_CERT` খালি (Caddy নিজেই সার্ট আনে)।

### ⚠️⚠️ `/opt/oxeio`-র বাইরের জিনিসগুলোই হারায়

rsync কোড · `.env` · `.data` সব এনেছে। কিন্তু **পাঁচটা জিনিস ওই ফোল্ডারের
বাইরে ছিল**, আর প্রতিটাই নীরবে ভাঙত:

| কী | কোথায় | না নিলে |
|---|---|---|
| B2-এর চাবি | `/etc/oxeio-offsite.env` | অফসাইট ব্যাকআপ বন্ধ |
| systemd unit ২টা | `/etc/systemd/system/` | টাইমারই থাকত না |
| **rclone** | `/usr/bin/rclone` | ⚠️⚠️ টাইমার চলত, কিন্তু **ব্যর্থ হতো** |
| GitHub deploy key | `/root/.ssh/` | `vps-update.sh` চলত না |
| `pull-backups.ps1`-এর ডিফল্ট IP | রেপোর ভেতরে | মালিকের PC-র তৃতীয় কপি বন্ধ |

⭐ **rclone-টা ধরা পড়েছে কেবল টাইমারটা হাতে চালিয়ে দেখায়** — অপেক্ষা
করলে ২৯ আগস্ট নীরবে ব্যর্থ হতো, আর জানা যেত সেদিন, যেদিন ব্যাকআপ লাগত।
⚠️ **শিক্ষা:** সরানোর পর প্রতিটা নির্ধারিত কাজ **একবার হাতে চালিয়ে**
দেখতে হয়; "ফাইলটা কপি হয়েছে" আর "কাজটা চলে" এক কথা নয়।

⚠️ কপি করতে গিয়ে আরও একটা জিনিস ধরা পড়ল: `/etc/oxeio-offsite.env`-এর
অনুমতি ছিল **644** — সার্ভারের যেকোনো ব্যবহারকারী B2-এর চাবি পড়তে
পারতেন। দুই সার্ভারেই **600** করা হয়েছে।

### বিকল্পগুলো — DNS-এর ২ ঘণ্টার লেজ

ExonHost-এর ফ্রি DNS **৭২০০-র নিচে TTL নেয় না** *("Value must be greater
than or equal to 7200")*। তাই ঘোরানোর পরেও কিছু PC পুরোনো IP-তে যেত।

| | কী | রায় |
|---|---|---|
| ক | পুরোনো সার্ভার চালু রেখে DNS ঘোরানো | ⛔ দুই ডাটাবেসে লেখা হতো, পরে জোড়া লাগত না |
| খ | পুরোনো Caddy-কে নতুনের দিকে proxy বানানো | ⚠️ কাজ করত, কিন্তু TLS · SNI · ক্লায়েন্ট-IP তিনটেই নতুন জটিলতা |
| **গ** | ⭐ **পুরোনোটা থামিয়ে রাতে সরানো** | ✅ বাছাই |

**সিদ্ধান্ত (গ)।** কারণ (খ) বানানোর আগে কোডে দেখা হয়েছে
(`src/oXeio.Core/Agent/OutboxBudget.cs:94`): এজেন্টের outbox **৭ দিন /
২ GiB** ধরে রাখে (সেগমেন্ট ৩০ দিন)। ⭐ **২ ঘণ্টার ব্যবধান ওখানে কিছুই নয়**
— proxy বানানো মানে ছিল একটা অ-সমস্যার জন্য তিনটে নতুন ঝুঁকি কেনা।

⭐ মাঠে লেজটা ২ ঘণ্টাও লাগেনি, **~১৪ মিনিট** — রেকর্ডটা অফিসের রিজলভারে
আগে থেকেই কিছুক্ষণ বসে ছিল, তাই বাকি আয়ু কম ছিল।

### ⚠️⚠️ যে ভুল মাপে এক ঘণ্টা নষ্ট হয়েছে

শুরুতে PowerShell-এর `TcpClient` দিয়ে পোর্ট পরীক্ষা করা হয়েছিল, আর সেখানে
`$c.Connected` **false** আসে দুই ক্ষেত্রেই — প্যাকেট হারালেও, আর সার্ভার
"এখানে কেউ নেই" বলে **RST পাঠালেও**।

⭐ **"Connection refused" আর "timeout" সম্পূর্ণ আলাদা খবর:** প্রথমটা মানে
প্যাকেট সার্ভার পর্যন্ত **পৌঁছেছে** (অর্থাৎ ফায়ারওয়াল খোলা), দ্বিতীয়টা
মানে পথেই হারিয়েছে। দুটোকে এক করে দেখানোয় ৪৪৩ খোলা থাকা সত্ত্বেও "বন্ধ"
পড়া হয়েছে, আর প্রোভাইডারের ফায়ারওয়াল নিয়ে অকারণ খোঁজাখুঁজি হয়েছে।

⚠️ **শিক্ষা:** যন্ত্র যা বলে তা নয়, যন্ত্র **কীভাবে** বলে সেটাও যাচাই করতে
হয়। `bash`-এর `/dev/tcp` দুটো অবস্থা আলাদা করে বলে — সেটাই ঠিক পরিমাপ।

### ⭐ আসল বাধা যা ধরা পড়ল

অফিসের ISP **বাইরে যাওয়ার পথে পোর্ট ২২ আটকায়** — মেপে: ২২ → ০/১০,
আর ৮০ · ৪৪৩ · ২২২২ → ১০/১০। USA সার্ভার থেকে ২২-ও খোলা পাওয়া গেছে,
অর্থাৎ দোষ সার্ভারের নয়।

⭐ কথাটা `deploy/vps-setup.sh`-এ **আগে থেকেই লেখা ছিল** (*"অনেক ISP
(যেমন AmberIT, বাংলাদেশ) বাইরের ২২ পোর্ট নীরবে আটকায়"*) — ডকটা আগে পড়লে
সময় বাঁচত।

⚠️⚠️ Ubuntu 24.04-এ SSH চলে **`ssh.socket`** দিয়ে (`ssh.service` নিষ্ক্রিয়),
তাই `sshd_config`-এ `Port 2222` লিখলে **কিছুই হয় না**। পোর্ট বসাতে হয়
`/etc/systemd/system/ssh.socket.d/`-তে, আর খালি `ListenStream=` দিয়ে আগের
তালিকা মুছতে হয় — নইলে ২২ দুবার বসে socket চালু হতে অস্বীকার করে।

### যাচাই — "সরানো হয়েছে" আর "ঠিক সরেছে" এক নয়

| কী | ফল |
|---|---|
| ফাইল | ১৮,২৩৪ → দুই দিকে হুবহু |

⚠️ **এজেন্ট সত্যিই ফিরেছে কি না, সেটা এই ADR লেখার সময় মাপা যায়নি** —

⭐ পার্শ্বফল: কাটাকাটির মুহূর্তে কেউ কিছু লিখছিলই না, তাই ঝুঁকি আরও কম ছিল।

## ADR-035 · অফিস বন্ধ থাকলে "এজেন্ট চুপ" অ্যালার্ট ✅ **তোলাই হবে না**

*২২ আগস্ট ২০২৬*

**প্রশ্ন:** মালিক Alerts পাতার ছবি পাঠিয়ে লিখলেন —
*"amader office sokal 9AM theke bikal 6PM prozonto. sabavik vabe office
close er pore agent gula down thakobe. seita abar alart kore dekhate hobe
ken?"* পাতায় তখন **২৫টা খোলা অ্যালার্ট**, প্রায় সবই `agent_down`।

### মাঠের মাপ — অভিযোগটা সংখ্যায়

১৪ দিনের `agent_down`, ঢাকার ঘণ্টা অনুযায়ী:

| ঘণ্টা | সংখ্যা | কী ঘটছে |
|---|---|---|
| **১৮** | ৯০ | অফিস ছুটি, PC নিভছে |
| **০০** | ৭৮ | ৬ ঘণ্টা পর **একই PC-র জন্য আবার** |
| **০৬** | ৭৮ | আরও ৬ ঘণ্টা পর, আবার |
| ১২ | ৩৩ | আরও ৬ ঘণ্টা পর (তখন অনেকে ফিরেছে) |

মোট ~৩৬৩টা, দিনে ~২৬টা।

⭐⭐ **গুচ্ছগুলোর ব্যবধান ঠিক ৬ ঘণ্টা — সেটাই `THROTTLE_HOURS`।** অর্থাৎ
রাতে একবার নয়, **একই PC সারা রাত ধরে তিনবার** অভিযোগ করে। এটা না মেপে
ধরা যেত না, আর না ধরলে "১৮টার অ্যালার্ট বন্ধ করলেই হবে" ভেবে অর্ধেক
সমাধান হতো।

### ⚠️ কেন আগের প্রহরীটা যথেষ্ট ছিল না

`isExpectedSilence()` আগে থেকেই ছিল: বিদায়ী ইভেন্ট (`agent_stop`,
`shutdown`, …) এলে নীরবতা ব্যাখ্যাত ধরা হয়। ⚠️ কিন্তু সেটা **ইভেন্ট
পৌঁছনোর উপর নির্ভরশীল** — Windows এজেন্টকে ৪ সেকেন্ডের বেশি সময় দেয় না
(`Program.ShutdownBudget`), তাই বিদায় প্রায়ই পৌঁছয়ই না। আর ঢাকনা বন্ধ
করা বা বিদ্যুৎ চলে যাওয়ায় তো প্রশ্নই ওঠে না।

⭐ মালিকের যুক্তিটা এর চেয়ে গভীর: **বিদায়ী ইভেন্ট এলেও না এলেও, অফিস
বন্ধ থাকলে PC নিভে থাকাটা খবরই নয়।** তাই সমাধান ইভেন্ট ঠিক করা নয়,
প্রশ্নটাই সময়ের বাইরে না করা।

### ⭐ ভুল কোন দিকে হবে — সেটাও একটা সিদ্ধান্ত

সময় **না বসানো থাকলে "সারাদিন খোলা"** ধরা হয়; একই নিয়ম বেঠিক লেখা
সময়ে (`9am`), আর উল্টো জানালায় (`১৮:০০–০৯:০০`)।

⚠️ কারণ ভুলের দুটো দিক সমান নয়: **বেশি অ্যালার্ট বিরক্তিকর, কিন্তু
নীরবে বন্ধ হয়ে যাওয়া পাহারা বিপজ্জনক** — কেউ টেরই পাবে না যে আর কেউ
দেখছে না। তাই সন্দেহ হলে সিস্টেম কথা বলার দিকেই ঝোঁকে।

### ⭐⭐ সংশোধন — অফিস খোলার পর ১৫ মিনিট ছাড় *(২৩ আগস্ট, পরদিনই)*

নিয়মটা বসার পরদিন সকালে মাঠে দেখা গেল: রাতে **০টা** অ্যালার্ট ✅, কিন্তু
ঠিক **৯:০০-এ ছটা**। আর ছটার সবাই **৯:০৯-এর মধ্যে ফিরে এসেছিলেন** —
অর্থাৎ একটাও আসল ছিল না।

⭐ কারণ সহজ: **অফিস ৯:০০-এ খোলে, কিন্তু মানুষ ৯:০০-এ এসে বসে PC চালু
করেন।** মেপে দেখা (২৩ আগস্ট): শুরুর সময় **০৮:৪৮ – ০৯:০৩**।

⚠️⚠️ ছাড় না দিলে এটা **রোজ** ঘটত — মাসে ~১৩০টা অকারণ অ্যালার্ট, আর
তাতেই আবার আসল খবর চাপা পড়ত। ঠিক সেই রোগ, যেটা [ADR-031] সারিয়েছিল।

**সমাধান:** `OFFICE_OPEN_GRACE_MIN = 15` — অফিস খোলার ১৫ মিনিট পর থেকে
পাহারা শুরু। ⭐ সবচেয়ে দেরিতে শুরু করা মানুষের চেয়েও ১২ মিনিট বেশি।

⚠️⚠️ **ছাড়টা কেবল শুরুতে, শেষে নয়** — বিকেলে কারো PC হঠাৎ বন্ধ হয়ে
যাওয়া সত্যিকারের খবর, আর ছুটির আগে সেটা চাপা পড়া উচিত নয়। একটা টেস্ট
ঠিক এই সীমারেখার পাহারাদার।

⭐ ফাংশনটা আলাদা — `isAgentWatchOpen()`, `isOfficeOpen()` নয়। *"অফিস কি
খোলা"* আর *"এখন কি সবার হাজির থাকার কথা"* দুটো আলাদা প্রশ্ন; একটাতে ছাড়
ঢোকালে সে নিজের নাম নিয়ে মিথ্যা বলত।

## ADR-036 · ডিজাইন গোনা ✅ **"খোলা" আর "শেষ" — দুটো আলাদা সংখ্যা**

> ⚠⚠ **প্রদর্শনের অংশটা বাতিল — [ADR-037](#adr-037--ডিজাইন-গোনা--কেবল-complete-খোলা-নয়) দেখুন *(২৩ আগস্ট ২০২৬)***। নিচের `/^(\d{3,7})(?!\d)/` নিয়মটা আর ক্রেডিট-মোছার সিদ্ধান্তটা **বহাল**; কেবল "পর্দায় দুটো সংখ্যা" আর "`met` খোলা ধরে" — এই দুটো উল্টে গেছে।

*২২ আগস্ট ২০২৬*

**প্রশ্ন:** মালিক জিজ্ঞেস করলেন *"akta designer koyta design korlo eTar ki
kOnO smart way ache?"* — খুঁজতে গিয়ে দেখা গেল **এখনকার পথটাই ভাঙা**।

### ⚠️⚠️ যে বাগটা প্রশ্নের উত্তর খুঁজতে গিয়ে বেরিয়ে এল

নিয়মটা ছিল `/^(\d{3,6})/` — **সীমানা যাচাই ছাড়া**। তাই সাত অঙ্কের সংখ্যা
পেলে সে প্রথম ছয়টা কেটে নিত:

| ফাইল | আগে | হওয়া উচিত |
|---|---|---|
| `1000042-Bird.ai` | `100004` | `1000042` |
| `1000043-Cat.ai` | `100004` ⚠️ **একই** | `1000043` |
| `10163372_181.eps` *(স্টক)* | `101633` ⚠️ গোনা হতো | বাদ |

⚠️⚠️ **টার্গেটের কাজের নম্বর শুরু হয়েছে ১০,০০,০০০ থেকে — সাত অঙ্ক।**
অর্থাৎ পরপর দশটা কাজ (`1000040`–`1000049`) **একটা বলে গোনা হতো**।

⭐ আর তার চেয়েও বড় ফল: `markStartedByJobNumbers()` মেলায় **হুবহু**
`jobNumber` ধরে, আর তাকে দেওয়া হচ্ছিল কাটা সংখ্যা। মাঠে মেপে:

```
job number সহ টার্গেট : 39,131
"শুরু" ধরা পড়েছে      :      0     ← একদিনও চলেনি
```

⚠️ আবারও সেই চেনা ব্যর্থতা — **যন্ত্রটা ঠিক লেখা ছিল, তাকে ভুল খোরাক
দেওয়া হচ্ছিল**।

### মাঠের প্রমাণ

`design_credits`-এ ৬৬টা ছয়-অঙ্কের সারি। শিরোনামে ওই ছয় অঙ্কের **পরেও
অঙ্ক ছিল কি না** দেখে আলাদা করা গেল:

| | সংখ্যা |
|---|---|
| প্রমাণিত কাটা-পড়া (স্টক ফাইল) | **৫০** |
| আসল ছয়-অঙ্কের কাজের নম্বর | ১৬ |
| অজানা | ০ |

⭐ ষোলোটা আসল থাকায় **"সব ছয়-অঙ্ক মুছে দাও" চলত না** — আগের হিস্টোগ্রামে
আসল নম্বরের সর্বোচ্চ ছিল ৯,৭৩,০৬৫, অর্থাৎ ছয় অঙ্ক বৈধ।

### বিকল্পগুলো — পর্দায় কোন সংখ্যা

| | কী | রায় |
|---|---|---|
| ক | শুধু Complete চাপা কাজ | ⚠️ কঠোর, কিন্তু কেউ চাপতে ভুললে কম দেখাত (এখনো ০ চাপ) |
| খ | শুধু ফাইলের নাম | ⚠️ "খোলা" বোঝায়, "শেষ" নয় |
| **গ** | ⭐ **দুটোই আলাদা** | ✅ মালিকের বাছাই |

**সিদ্ধান্ত (গ)।** পর্দায় `Designs · opened / done` —
`১৮ · ১২ / ২৫` মানে ১৮টা ফাইল খোলা, ১২টা শেষ বলা, টার্গেট ২৫।

⚠️ **শূন্য হলে "শেষ"-এর ঘরটা খালি থাকে, "০" নয়** — বোতামটা সবে বসেছে,
আর "১৮ · ০" দেখতে "কিছুই হয়নি"-র মতো লাগত, অথচ আসল কথা কেউ এখনো
বোতামটা ব্যবহার করছেন না। দুটো আলাদা ব্যাপার।

### ⚠️ ✅ চিহ্নটা এখনো "খোলা" ধরে — ইচ্ছাকৃত

টার্গেট ছোঁয়ার হিসাব `designsDone` (খোলা) ধরেই থাকল। ⚠️ এখনই "শেষ"-এর
সাথে বাঁধলে **পরদিন সকালে সবাই টার্গেট-মিস** দেখাতেন, কারণ Complete
বোতামে মাঠে **০টা চাপ** পড়েছে। ⭐ বোতামটা অভ্যাসে দাঁড়ালে এটা এক লাইনে
বদলানো যাবে, আর টেস্টটা সেই সিদ্ধান্তের পাহারাদার হয়ে রইল।

### ✅ পুরোনো ভুল ক্রেডিট মোছা হয়েছে *(মালিকের নির্দেশ, একই দিনে)*

মালিক: *"muche dao"*। ⚠️ ঢালাওভাবে নয় — কেবল **প্রমাণিত** ৫০টা সারি
(৪৯টা আলাদা নম্বর), আর ১৬টা আসল ছয়-অঙ্কের নম্বর অক্ষত।

⚠️⚠️ **শুধু ক্রেডিট মোছাই যথেষ্ট ছিল না** — সংখ্যাগুলো `daily_summary`-তেও
বসে গিয়েছিল। শুধু একদিকে মুছলে Live Board (ক্রেডিট পড়ে) আর রিপোর্ট
(সারাংশ পড়ে) **দুই সংখ্যা দেখাত**। তাই একই লেনদেনে ৩০টা দিনের সারাংশ
আবার গোনা হয়েছে। ⭐ মোছার আগে পুরো ডাটাবেসের ডাম্প রাখা হয়েছে।

শেষে অমিল: **০**।

### ⚠️⚠️ সংশোধন — একই দিনে, মোছার পরেই

মোছার পর দেখা গেল **সাত-অঙ্কের চারটে নতুন ক্রেডিট** ঢুকেছে, আর কোনোটাই
আসল কাজের নম্বর নয় — `1536601` · `5005369` · `5524618` · `9937760`,
সবই স্টক-আইডি।

⭐ অর্থাৎ `৩–৭ অঙ্ক` নিয়মটা সাত-অঙ্কের স্টক ফাইলকেও ঢুকতে দেয়। **অঙ্ক
গুনে অনুমান করা যথেষ্ট নয়** — নিখুঁত পার্থক্য একটাই: *নম্বরটা কি সত্যিই
কাউকে দেওয়া হয়েছিল?*

তাই এখন: **১০,০০,০০০-এর সমান বা বেশি নম্বর তখনই গোনা হয়, যখন সেটা
`design_targets.job_number`-এ আছে** (`keepKnownLongIds()`)।

⚠️ ছয় অঙ্ক বা কম **এই শর্তের বাইরে** — পুরোনো কাজের (৩৭৯৩৩ ধাঁচের) কোনো
টার্গেট-সারি নেই; শর্তে ফেললে পুরো ইতিহাস নীরবে শূন্য হয়ে যেত। একটা
টেস্ট ঠিক সেই ভুলের পাহারাদার।


## ADR-037 · ডিজাইন গোনা ✅ **কেবল Complete, খোলা নয়**

*২৩ আগস্ট ২০২৬* — [ADR-036](#adr-036--ডিজাইন-গোনা--খোলা-আর-শেষ--দুটো-আলাদা-সংখ্যা)-এর প্রদর্শন-সিদ্ধান্ত বাতিল করে।

**যেভাবে ধরা পড়ল।** মালিক Live Board-এ ম্যানেজারের (OX-01) পাশে **১৬**
দেখে জিজ্ঞেস করলেন *"belal 16 ta design koreche? kivabe pele ei data?"* —
প্রশ্নটাই সঠিক ছিল। মেপে দেখা গেল তিনি ১৯টা ফাইলে মোট **৪৪ মিনিট**
দিয়েছেন, অর্থাৎ **খুলে দেখছিলেন, বানাননি**।

এরপর নির্দেশ: *"file khoila hole seta count koro na, only complet dile
count koro"*।

### ⭐ মাঠের মাপ — নতুন নিয়মই বেশি সত্য

২৩ আগস্টের সংখ্যা (`design_credits.first_work_date` বনাম
`design_targets.completed_at`):

| কর্মী | খোলা *(পুরোনো)* | শেষ *(নতুন)* | |
|---|---|---|---|
| **OX-01** *(ম্যানেজার)* | **১৭** | **০** | ⚠️ যে সংখ্যাটা নিয়ে প্রশ্ন |
| **OX-06** | ৫ | **১৫** | ⚠️⚠️ পুরোনো নিয়ম **তিন গুণ কম** দেখাত |
| OX-07 | ১৩ | ১৩ | |
| OX-08 | ১৫ | ১২ | |
| OX-13 / OX-11 | ৬ / ৬ | ০ / ০ | |

⭐⭐ **সবচেয়ে জরুরি সারিটা OX-06-এর।** "খোলা" সংখ্যাটা কেবল বেশিই দেখাত
না — কমও দেখাত। একই ফাইল দুদিন ধরে করলে `design_credits` তাকে **প্রথম
দিনে** ধরে (`first_work_date`), তাই শেষ করার দিনে সে অদৃশ্য।

### ⚠️ ADR-036-এর যুক্তিটা মরে গেছে, আর সেটাই বদলের অনুমতি

ওখানে লেখা ছিল *"`met` খোলা ধরেই থাকল, কারণ Complete বোতামে মাঠে **০**
চাপ"*। আজকের হিসাব:

```
23 Aug: Complete চাপা পড়েছে 53 বার, 6 জন ব্যবহারকারী
```

⭐ বোতামটা অভ্যাসে দাঁড়িয়ে গেছে — ADR-036 নিজেই বলেছিল *"দাঁড়ালে এটা এক
লাইনে বদলানো যাবে"*। শর্তটা পূরণ হয়েছে, তাই বদলানো হলো।

### বিকল্পগুলো

| | কী | রায় |
|---|---|---|
| ক | দুটো সংখ্যাই রাখা | ⚠️ মালিক নিজেই ভুল পড়েছেন — দুটো সংখ্যা পড়তে হয় বলেই |
| খ | খোলা রাখা, শেষ বাদ | ⚠️⚠️ ঠিক যে মিথ্যাটা ধরা পড়েছে |
| **গ** | ⭐ **কেবল শেষ** | ✅ মালিকের নির্দেশ |

**সিদ্ধান্ত (গ)।** পর্দায় এখন একটাই সংখ্যা — `১৫ / ২৫`।

### ⚠️⚠️ কাকে ক্রেডিট — বোতাম যে চাপল, নাকি যার কাজ

`design_targets`-এ দুটো আলাদা ঘর, আর **দুটো আলাদা টেবিলের দিকে**:

| ঘর | দেখায় |
|---|---|
| `completed_by_id` | **`users(id)`** — কে বোতামটা চাপল |
| `assigned_to_id` | **`employees(id)`** — কার কাজ |

⭐ গোনা হয় `assigned_to_id` ধরে। ⚠️⚠️ id-র জগৎ দুটো **আলাদা** (কর্মী
১০, ১৭–২৮; ব্যবহারকারী ৪, ৫, ৬, ৯, ১১, ১৩) — ভুল ঘরটা ধরলে সংখ্যা
বেশিরভাগ ক্ষেত্রে **নীরবে শূন্য**, আর id মিলে গেলে **ভুল লোককে ক্রেডিট**।
ম্যানেজার কারো হয়ে Complete চাপলেও ক্রেডিট ডিজাইনারেরই থাকে।

### যেখানে যেখানে বদলাল — ছটা জায়গা, একটাও বাদ নয়

⚠️ আগেরবারের শিক্ষা *("চুক্তি লেখা আছে, কলার লেখা হয়নি")* মাথায় রেখে
প্রতিটা প্রদর্শন-বিন্দু ধরে ধরে বদলানো হয়েছে:

| জায়গা | ফাইল |
|---|---|
| Live Board টাইল | `web/src/pages/LiveBoardPage.tsx` |
| Live Board টেবিল ও কার্ড | `web/src/pages/live/DesignCell.tsx` |
| টার্গেট ছোঁয়ার হিসাব | `web/src/pages/live/roster.ts` |
| Reports → Attendance | `web/src/pages/reports/AttendanceTab.tsx` |
| Excel রপ্তানি | `server/src/reports/reports.sheets.ts` |
| Telegram দৈনিক সার | `server/src/digest/digest.service.ts` |

⚠️ `daily_summary.designsDone` আর পড়া হয় না — ওটা "খোলা"-র সংখ্যা।
সারণিটা রয়ে গেছে, কারণ ওতে সময়ের হিসাবও আছে।

### ⚠️ যা মেনে নেওয়া হয়েছে

কেউ Complete চাপতে ভুললে তাঁর দিনটা **০** দেখাবে। ⭐ এটা বাগ নয়,
সিদ্ধান্ত — "মাপা যায়নি" আর "কাজ হয়নি" এক করে দেখানোর চেয়ে কম দেখানো
ভালো, কারণ ০ দেখলে কেউ জিজ্ঞেস করেন; বাড়িয়ে দেখালে কেউ করেন না।

## ADR-038 · শনিবারের বানান-যাচাই ⏳ **নকশা চূড়ান্ত, কোড শুরু হয়নি**

*২৪ আগস্ট ২০২৬*

মালিক অফিসের আসল ওয়ার্কফ্লোটা লিখে দিয়ে জিজ্ঞেস করলেন *"ei puro workflow
ta ki amora software kore felote pari?"*

```
১· গবেষকরা target design list collect করে          ✅ আছে
২· ডিজাইনাররা target নিয়ে re-design করে             ✅ আছে
৩· প্রতি শনিবার সব ডিজাইন collect করা হয়            ⏳ অর্ধেক
৪· spelling check করা হয়                            ⏳ হিসাবটুকু
৫· ভুল পেলে বেলাল fix করে                            ⏳
৬· বাকি fix শেষে Complete ফোল্ডারে দেওয়া হয়         ⏳ বোতামটুকু
```

### ⭐ মালিকের তিনটে উত্তর *(২৪ আগস্ট)*

| প্রশ্ন | উত্তর | কী বদলাল |
|---|---|---|
| যাচাই একটা-একটা, নাকি গুচ্ছ ধরে? | **একটা একটা করে** | প্রতি সারিতে দুটো বোতাম — গুচ্ছ-বোতাম বানানো হবে না |
| বানান কে দেখেন? | ⭐ **সুমাইয়া (OX-04), গবেষক** — বেলাল নন | যাচাই আর ঠিক-করা **দুজন আলাদা মানুষ**, তাই ধাপ দুটো মেলানো যাবে না |
| শনিবার ছাড়া হয়? | **"শনিবার" তুলে দাও** | কোনো সাপ্তাহিক cron নয় — সারিটা **রোজই খোলা**, শনিবারে শুধু লম্বা |

⭐⭐ **তৃতীয় উত্তরটাই নকশার সবচেয়ে বড় সরলীকরণ।** কোনো "ব্যাচ" সত্তা নেই,
কোনো সপ্তাহ-শুরু/শেষ নেই — **সারিটাই ব্যাচ**। যা শেষ হয়েছে অথচ যাচাই হয়নি,
তা নিজে থেকেই জমতে থাকে। ⚠️ এই প্রকল্পে যা-কিছু মনে রেখে খুলতে হয় তা-ই
মাঠে ব্যর্থ হয়েছে; যা নিজে থেকে জমে তা-ই টিকেছে।

### ⚠️ অনুমতি — নতুন রোল লাগছে না

সুমাইয়ার রোল `employee`, কিন্তু `assertCanUse()` পাহারা দেয়
**`staffType`** ধরে (`owner | manager | researcher`), রোল ধরে নয়। তাই
গবেষক হিসেবে তিনি এমনিতেই টার্গেট-তালিকা ছুঁতে পারেন।

### ⚠️⚠️ যে মাপটা নকশার ভিত নড়িয়ে দিল

```
কে টার্গেট যোগ করেছেন :  owner 39,131 · বেলাল 6,528 · গবেষক  0
গবেষকদের শেষ লগইন    :  দুজনেরই ১৩ আগস্ট — সিস্টেম চালুর দিন
৯ জন ডিজাইনার        :  সবাই ২৩ আগস্ট
```

⭐⭐ অর্থাৎ Design Pool যাঁদের জন্য বানানো, সেই **গবেষকরা একটাও টার্গেট
যোগ করেননি**, আর ১১ দিন পোর্টাল খোলেননি। ডিজাইনাররা রোজ খোলেন, কারণ
তাঁদের টার্গেট আর Complete বোতাম ওখানেই — **পোর্টাল তাঁদের পথে পড়ে**।

⚠️ সুমাইয়ার জন্য একটা যাচাই-পর্দা বানানো মানে এমন একজনের জন্য বানানো
যিনি আজ পোর্টাল ব্যবহারই করেন না। এটা "না" নয় — কিন্তু নকশাটা এই সত্যটা
জেনে করতে হবে, নইলে ঠিক আগেরগুলোর মতোই হবে: কারিগরিভাবে নিখুঁত, মাঠে ০।

### ⏳ যা এখনো ঠিক হয়নি

মালিককে জিজ্ঞেস করা হয়েছে — গবেষকদের পোর্টাল ব্যবহার না করাটা
প্রত্যাশিত কি না, আর যাচাইয়ের কাজটা সুমাইয়ার কাছে **কীভাবে পৌঁছাবে**।
⚠️ এই উত্তর ছাড়া কোড শুরু করা হবে না।

### যা সফটওয়্যার পারবে না — লিখে রাখা

| | কেন |
|---|---|
| যন্ত্র নিজে বানান ভুল ধরবে | লেখা `.ai`/`.psd`-র ভেতরে; নীতিমালায় *"ফাইল খোলা বা পড়া হয় না"*, আর স্ক্রিনশট OCR লিখিতভাবে বাদ। ⚠️ তাছাড়া টি-শার্টের লেখা প্রায়ই outline করা — তখন ওটা ছবি |
| ফোল্ডারে ফাইল পড়লে নিজে ধরবে | মাঠে মাপা: OX-06 ১৫টা শেষ করেছেন, ফাইলের নামে নম্বর ছিল **৫টায়** — স্ক্যান করলে দুই-তৃতীয়াংশ নীরবে হারাত |

### ⚠️ নতুন ধাপ **Status-এ ঢুকবে না**

আজ যত জায়গায় "কতগুলো ডিজাইন হয়েছে" গোনা হয় সবই `done` ধরে গোনে। নতুন
অবস্থা বানালে সারি `done` থেকে সরে গিয়ে **সব সংখ্যা নীরবে কমে যেত**।
⭐ তাই প্রমাণিত ধাঁচেই — `uploadedAt`/`liveAt`-এর মতো **তারিখ ও নাম**,
অবস্থা নয়।

সম্পূর্ণ নকশা: [09 § ৩ঞ৮](09-Build-Log.md)।

## ADR-039 · গবেষকের কাজের কিউ ✅ **নতুন পাতা নয়, দুটো চিপ**

*২৪ আগস্ট ২০২৬*

**মালিকের নির্দেশ:** *"researcher der jonno web portale kiso ekta banano
jete pare"* — এসেছে এই মাপটা দেখার পর:

```
গবেষকরা কতগুলো টার্গেট যোগ করেছেন :  ০
তাঁদের শেষ লগইন                    :  দুজনেরই ১৩ আগস্ট (সিস্টেম চালুর দিন)
৯ জন ডিজাইনারের শেষ লগইন           :  সবাই গতকাল
```

### ⭐⭐ আবিষ্কার: তাঁদের কাজটা কোডে ইতিমধ্যেই ছিল

`targets.controller.ts`-এর মন্তব্যেই লেখা: *"আপলোড হয়েছে — owner ·
manager · **গবেষক**। ⚠️ ডিজাইনার নন"*। বোতাম দুটোও প্রতিটা সারিতে ছিল।

⚠️ যা ছিল না: **"কোনগুলো"** — ৩৯ হাজার সারির স্তূপ থেকে আজকের কাজটা
আলাদা করার উপায়। ফলে ২৭,৬৩২টার মধ্যে বোতামটা চাপা পড়েছিল **১ বার**।

### সিদ্ধান্ত — যা করা হয়েছে

| | |
|---|---|
| **নতুন পাতা** | ❌ নয় — নেভে ইতিমধ্যেই ৫টা আইটেম, ষষ্ঠটা হারাত। যে পাতায় বোতাম আছে সেখানেই দুটো চিপ |
| **চিপ দুটো** | `To upload · N` আর `To make live · N`, তালিকার **শুরুতে** |
| **সংখ্যা চিপেই** | ⭐ ক্লিক করার **আগেই** জানা দরকার আজ কাজ আছে কি না |
| **লগইনের পর** | গবেষক নামবেন `/targets/all`-এ, `/me`-তে নয় |
| **Delete** | ⚠️ কেবল owner ও manager — নিচে দেখুন |

### ⚠️⚠️ কাটা-তারিখ: ২৩ আগস্ট *(মালিকের সিদ্ধান্ত)*

২২ আগস্টের ইমপোর্টে **২৭,৫০৯টা** পুরোনো `done` সারি ঢুকেছে (সবচেয়ে
পুরোনোটা জানুয়ারি ২০২৫) — ওগুলো অনেক আগেই Amazon-এ গেছে, তখন বোতামটাই
ছিল না।

```
সীমা ছাড়া  →  ২৭,৬৪১ বাকি   ⚠️ কিউ নয়, পাহাড় — কেউ শুরুই করত না
২৩ আগস্ট থেকে →    ১৩২ বাকি   ✅ এক দিনের কাজ
```

⭐ ২৩ আগস্ট বাছা হয়েছে কারণ **ওই দিনই Complete বোতাম মাঠে চলতে শুরু করে**
(২২ আগস্ট ০ চাপ → ২৩ আগস্ট ৫৩ চাপ)। ধ্রুবকটার নাম `UPLOAD_QUEUE_FROM`,
আর কারণটা ওখানেই লেখা — জাদু-সংখ্যা নয়।

⚠️ `to_live`-এ কাটা-তারিখ **নেই**, দরকারও নেই — Uploaded চাপা সারিই মাত্র ১টা।

### ⚠️ নতুন ধাপ Status-এ ঢোকেনি

`uploaded`/`live` **তারিখ**, অবস্থা নয় — আর সেটা ইচ্ছাকৃত। অবস্থা বানালে
সারিটা `done` থেকে সরে গিয়ে **সব "কতগুলো ডিজাইন হয়েছে" গণনা নীরবে কমে
যেত**। কিউ দুটোও তাই `status` নয়, আলাদা `stage` ছাঁকনি।

### ⚠️⚠️ পথে পাওয়া নিরাপত্তা-ফাঁক

Design Pool পাতাটা `useAuth` **ডাকতই না**, তাই প্রতিটা সারিতে ছটা বোতামই
শর্তহীন ছিল — **Delete সহ**। কেউ পাতাটা খুলত না বলে চোখে পড়েনি।

⭐ এখন গবেষককে রোজ ওই পাতায় পাঠানো হচ্ছে, তাই আগে বিপজ্জনক বোতামটা তুলে
নেওয়া হয়েছে। ⚠️ মুছলে ডুপ্লিকেট-প্রহরী ওই ASIN **ভুলে যায়**, অর্থাৎ কাল
কেউ আবার জমা দিলে পুরোনো কাজ নতুন হয়ে ঢুকত — ফেরানোর উপায় নেই।

### ⭐ যা ইচ্ছাকৃতভাবে বানানো হয়নি

| | কেন |
|---|---|
| "আমার আনা লিঙ্ক" ব্যক্তিগত টাইল | গবেষকরা আজ পর্যন্ত **০টা** এনেছেন — আয়নাটা চিরকাল শূন্য দেখাত |
| "পুল আর কত দিন চলবে" | পুলে **৫২ দিনের কাজ**; উত্তরটা সবসময় "আজ কিছু করার নেই" |
| গবেষকের দৈনিক টার্গেট | স্কিমায় ঘর নেই, আর কিউ-এর সংখ্যাটাই নিজেই টার্গেট |
| বানান-যাচাই ([ADR-038](#adr-038--শনিবারের-বানান-যাচাই--নকশা-চূড়ান্ত-কোড-শুরু-হয়নি)) | আলাদা কাজ — গোটা পোর্টালকে একটা অলিখিত ফিচারের পেছনে আটকে রাখা যেত না |

### মাপার নিয়ম — এক সপ্তাহ পরে

⭐ দুটো সংখ্যা, আর কেবল ওই দুটোই বলবে কাজ হলো কি না:
**OX-04/OX-05-এর `last_login_at`** (আজ পর্যন্ত ১৩ আগস্টেই আটকে), আর
**`uploadedAt` গোনা** (আজ ১)। না নড়লে আরও কোড লেখা ভুল উত্তর।
